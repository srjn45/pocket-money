## 0. Summary

The monthly statement is **derived** — no new tables, no new migration (§3.9:
"No new tables"). Per `(group, member, month M)` it is computed from the approved
ledger after `PostDue` materializes that month's system entries. It answers the
product's central question: for month M, what did each member earn, what was
paid, and what remains.

The endpoint returns, for month M:

- **admin caller** → one row per **non-admin member** (the recipients) whose join
  month ≤ M, plus a **group total**;
- **member caller** → **their own single row only** (D6), no group total.

Each row carries the §3.9 figures as `Money{currency,value}`:
`opening_balance`, `base`, `chores`, `adjustments`, `emi`, `total_due`,
`cleared`, `closing_balance`, plus the member's ordered ledger rows for M (the
month passbook).

**The core invariant** — `closing(M) == opening(M+1)` — holds **by construction**
(§2.4) and is proven by a pure-function property test (`TestCompute_ClosingEquals
NextOpening`, runs locally) **and** an integration test across a 3-month backfill
(`TestStatement_ClosingEqualsNextOpening_Backfill`, CI-only).

### 0.1 Two pieces of work

1. **Pure statement engine** — `backend/internal/statement` package: a
   dependency-free `Compute(entries, month)` that turns one member's approved
   ledger entries + a target month into the eight figures + the month's rows.
   **Unit-tested with NO database** (no `//go:build integration` tag) — this is
   where the invariant and every edge case are proven locally, since Docker is
   unavailable on the dev host (§9.3).
2. **HTTP handler + openapi** — `GET /api/v1/groups/{id}/statement?period=YYYY-MM`
   wired onto the existing `LedgerHandler` (it already holds `ledgerRepo`,
   `groupRepo`, `choreRepo`, `postingSvc` — no new constructor), reusing the
   existing `Money` machinery, `PostDue`, D6 scoping pattern, and
   `groups.currency` (D7). openapi is the serial touch (§9.1).

## 1. Entry-type mapping (plan concept name → DB/API type)

§3.5/§3.9 use **concept** names; the shipped DB + API `entry_type` enum
(`models.LedgerEntryType`, openapi) uses the **v2** names. The statement math is
defined on the **DB names**. This mapping is authoritative for this WP:

| §3.9 concept | statement figure | DB `entry_type` | `direction` | sign in Σ |
|---|---|---|---|---|
| `base_credit` | `base` | `allowance` | `credit` | `+amount` |
| `chore_credit` | `chores` | `chore` | `credit` | `+amount` |
| `adjustment` | `adjustments` | `adjustment` | `credit` **or** `debit` | `±amount` |
| `emi_debit` | `emi` | `emi` | `debit` | `−amount` |
| `clearing` (D9 "payment") | `cleared` | `settlement` | `debit` | `−amount` |

> **⚠ FLAG (naming, not a blocker for V3-3.1):** D9 and §3.9 call the payment
> entry `clearing`; the shipped type is **`settlement`** (§3.4: "the v2
> 'Settlement' system chore remains the internal vehicle for clearings"). This WP
> **uses `settlement`** as the clearing/payment vehicle and does **not** rename
> it — a rename would be a fresh migration + openapi enum change, out of scope
> here. Renaming `settlement`→`clearing` should be tracked as its own WP (natural
> fit alongside V3-3.2 corrections). No money/auth semantics are ambiguous; only
> the label differs, so this is a note, not a §10 stop.

**Signed amount** (used everywhere below): `signed(e) = +e.Amount` when
`e.Direction == credit`, `−e.Amount` when `debit`. `e.Amount` is always a
non-negative int64 magnitude (matches `LedgerResponse` "value is always positive;
direction indicates credit/debit"). Only **`status = approved`** entries count —
pending/rejected are excluded, identical to `GetBalanceForGroup`/`MemberBalance`.

## 2. Balance semantics (the math — precise)

### 2.1 The effective month of an entry (the critical rule)

Each entry belongs to **exactly one** month, `effMonth(e)`:

```
effMonth(e) = e.Period                         if e.Period != nil   // allowance, emi (system)
            = formatPeriodLocal(e.CreatedAt)    otherwise            // chore, settlement, adjustment (manual)
formatPeriodLocal(t) = t.Local().Format("2006-01")
```

- System entries (`allowance`, `emi`) always carry `period` (`YYYY-MM`) — set by
  the posting engine — so their month is unambiguous and stable.
- Manual entries (`chore`, `settlement`, `adjustment`) have `period == NULL`;
  their month is the **calendar month of `created_at`, in server-local time**
  (§9.7: periods are `YYYY-MM`, server-local, the server is the clock).

> **⚠ IMPLEMENTATION HAZARD (must be honored):** `pgx` returns `timestamptz`
> (`created_at`) as a `time.Time` in **UTC**. `PostDue` derives periods from
> `time.Now()` which is **server-local**. To bucket manual entries into the same
> calendar the system entries use, you **must** convert: `t.Local()` before
> `Format("2006-01")`. Formatting the raw UTC value would mis-bucket entries
> created near a month boundary (e.g. `2026-07-31 23:30` local, stored
> `2026-08-01 03:30Z` in a UTC+? DB) into the wrong month and could break the
> invariant tests. `formatPeriodLocal` centralizes this; do not inline a raw
> `Format`.

> **NOTE — this differs from the ledger `?period=` filter.** `GET .../ledger?
> period=X` filters on the `period` **column** (NULL for manual entries), so it
> returns only system entries of month X. The **statement** intentionally uses
> `effMonth` (COALESCE of `period` and month-of-`created_at`) so a chore/payment
> lands in the month it was recorded. These two notions of "month" are different
> **by design**; do not "fix" one to match the other.

### 2.2 The five figures within month M (for one member)

Over that member's approved entries `e` with `effMonth(e) == M`:

```
base(M)        = Σ e.Amount        where entry_type = allowance     (credit; ≥ 0)
chores(M)      = Σ e.Amount        where entry_type = chore          (credit; ≥ 0)
adjustments(M) = Σ signed(e)       where entry_type = adjustment     (± ; may be negative)
emi(M)         = Σ e.Amount        where entry_type = emi            (debit magnitude; ≥ 0)
cleared(M)     = Σ e.Amount        where entry_type = settlement     (debit magnitude; ≥ 0)
```

### 2.3 Opening, total due, closing

```
opening(M)  = Σ signed(e)   over ALL approved entries of the member with effMonth(e) <  M   // D1 carryover
earned(M)   = base(M) + chores(M) + adjustments(M) − emi(M)
total_due(M)= opening(M) + earned(M)
closing(M)  = total_due(M) − cleared(M)
```

**Sign convention** (matches the existing `BalanceResponse.balance` = Σ credits −
Σ debits): a **positive** balance means money is owed **to the member** ("you'll
receive ₹X"); negative means the member owes. `opening_balance`, `adjustments`,
`total_due`, `closing_balance` are therefore **signed** `Money` (value may be
negative — legitimate and consistent with `BalanceResponse`). `base`, `chores`,
`emi`, `cleared` are non-negative magnitudes.

### 2.4 The invariant — `closing(M) == opening(M+1)` — holds *by construction*

Expand `closing` in signed terms. `base + chores` are credit sums; `−emi` and
`−cleared` are debit magnitudes subtracted; `adjustments` is already signed.
Hence:

```
closing(M) = opening(M) + [ base + chores + adjustments − emi − cleared ]
           = opening(M) + Σ signed(e) over entries with effMonth(e) == M
           = Σ signed(e) over effMonth(e) < M   +   Σ signed(e) over effMonth(e) == M
           = Σ signed(e) over effMonth(e) ≤ M
           = Σ signed(e) over effMonth(e) < (M+1)
           = opening(M+1)                                                  ∎
```

The proof needs only three properties, all guaranteed by `Compute`:

1. **Every entry maps to exactly one month** via the single `effMonth` function
   (§2.1) — used identically for the `< M` (opening) bucket and the `== M`
   bucket, so no entry is double-counted or dropped.
2. **`signed()` is one function**, used identically in `opening` and in the
   in-month figures (`cleared` is a `settlement` **debit**, already part of
   `Σ signed`, so subtracting it does not double-count).
3. **The same currency** throughout (D7, §3) — no cross-currency term ever
   enters a sum (§3, single group currency; asserted in tests, §4).

Because it is structural, the invariant holds for **empty months, month
boundaries, partial-type months, and future months** with no special-casing.

### 2.5 `Compute` — the pure function (single source of truth for the math)

```go
// package statement  (backend/internal/statement/statement.go)

// MemberStatement is one member's derived figures for a month, in int64 minor
// units (currency applied at the handler boundary). Signed fields may be < 0.
type MemberStatement struct {
    Opening     int64 // Σ signed(e), effMonth < M       (signed)
    Base        int64 // Σ allowance credit in M          (≥ 0)
    Chores      int64 // Σ chore credit in M              (≥ 0)
    Adjustments int64 // Σ signed adjustment in M         (signed)
    EMI         int64 // Σ emi debit magnitude in M       (≥ 0)
    TotalDue    int64 // Opening + Base + Chores + Adjustments − EMI  (signed)
    Cleared     int64 // Σ settlement debit magnitude in M (≥ 0)
    Closing     int64 // TotalDue − Cleared                (signed)
    Entries     []*models.LedgerEntry // month M rows for this member, created_at ASC
}

// Compute derives one member's statement for `month` (YYYY-MM) from ALL of that
// member's approved ledger entries (any month, any type). Pure: no I/O, no clock
// beyond time.Time.Local() on each entry's CreatedAt. Deterministic.
func Compute(entries []*models.LedgerEntry, month string) MemberStatement
```

- Caller passes only `status == approved` entries (handler filters via the repo);
  `Compute` additionally ignores any non-approved defensively.
- `Entries` are the `effMonth == month` subset, sorted `created_at` ASC
  (chronological passbook order; the repo returns DESC, so `Compute` sorts).
- `Compute` never looks at `groups.currency` — currency is a handler concern
  (D7). It works purely in minor units.

## 3. Endpoint contract

### 3.1 Route

```
GET /api/v1/groups/{id}/statement?period=YYYY-MM[&user_id=UUID]
```

Registered in `cmd/server/main.go` next to the other `groups/:id` reads:
`protected.GET("/groups/:id/statement", ledgerHandler.GetStatement)`.

### 3.2 Parameters

| Param | In | Req | Notes |
|---|---|---|---|
| `id` | path | yes | Group UUID. Non-UUID → 400. |
| `period` | query | **no** | `YYYY-MM`. **Defaults to the current server-local month** (`formatPeriodLocal(time.Now())`) when omitted. Malformed → 400 (reuse `isValidPeriod`). |
| `user_id` | query | no | Admin: narrow to one member's row (group total then omitted, §3.4). Member: may pass **only their own** id; any other → **403** (mirror `ListLedger`, V3-2.2). |

### 3.3 Auth / scoping (D6 — reconciled with V3-2.2)

1. Resolve caller from JWT (`auth.GetUserID`); parse `id`.
2. `groupRepo.GetMember(group, caller)` → `ErrNotFound` ⇒ **403** ("not a member
   of this group"). This membership gate runs **before** `PostDue` (mirrors
   `GetBalance`/`ListLedger`, §9.10).
3. `runPosting(c, postingSvc, groupID)` — materialize due `allowance`/`emi`
   entries **before** reading (balance-sensitive; same as `GetBalance`).
4. Role branch (D6, §4 matrix "View statement — admin: whole group; member: own
   rows only"):
   - **admin** → all **non-admin** members with join-month ≤ M (§3.5), each a
     `MemberStatementResponse`; `group_total` present (unless `user_id` narrows
     to one, §3.4).
   - **member** → exactly one element: **their own** row; `group_total`
     **omitted/null**. A member requesting `user_id=<someone-else>` → 403; a
     member requesting their own pre-join month → `members: []`, 200 (§3.6).

**Currency (D7):** taken **solely** from `groupRepo.GetCurrency(groupID)`. There
is **no currency request field** anywhere on this endpoint — nothing to validate,
nothing to reject; the response stamps that one currency on every `Money`.

### 3.4 Admin exclusion & group total (consistency with existing balance)

The existing `GetBalanceForGroup` **excludes the admin's own row** (recipients
only) and members never see totals. The statement mirrors this:

- `members[]` = non-admin members only (the pocket-money recipients).
- `group_total` = element-wise Σ over the **returned** members, present **only**
  on the unfiltered admin view (no `user_id`). When an admin narrows via
  `user_id`, `group_total` is omitted. Never present for a member caller.

> This "recipients only, admin excluded" choice is **inherited from the shipped
> `GET /balance` behavior**, not a new decision — kept for consistency. If the
> product later wants the admin as a tracked member too, that is a balance-wide
> change, not a statement-only one.

### 3.5 "Months before a member's join return no row" (§8)

A member is included for month M iff `M >= joinMonth(member)` where
`joinMonth = formatPeriodLocal(joined_at)` from `groupRepo.ListMembers` (returns
`joined_at`). Because `PostDue` floors posting at the join month, a member has no
system entries before joining, and (being a non-member earlier) no manual entries
either — so their `opening(joinMonth) == 0` falls out naturally (§3.6 first-ever
month). Members whose join month > M are simply absent from `members[]`.

### 3.6 Response schema (openapi component names in §5)

```jsonc
// 200 OK
{
  "group_id": "…uuid…",
  "period":   "2026-07",
  "currency": "INR",                       // convenience; also on every Money
  "members": [
    {
      "user_id": "…uuid…",
      "name": "Aanya",
      "opening_balance": { "currency": "INR", "value":  50000 },  // signed
      "base":            { "currency": "INR", "value": 100000 },
      "chores":          { "currency": "INR", "value":  15000 },
      "adjustments":     { "currency": "INR", "value":  -2000 },  // signed (debit adj)
      "emi":             { "currency": "INR", "value":  30000 },
      "total_due":       { "currency": "INR", "value": 133000 },  // opening+base+chores+adj−emi
      "cleared":         { "currency": "INR", "value": 120000 },
      "closing_balance": { "currency": "INR", "value":  13000 },  // total_due−cleared → next opening
      "entries": [ /* LedgerResponse[], effMonth==period, created_at ASC */ ]
    }
  ],
  "group_total": {                          // admin unfiltered only; omitted for member
    "opening_balance": { "currency": "INR", "value":  50000 },
    "base":            { "currency": "INR", "value": 100000 },
    "chores":          { "currency": "INR", "value":  15000 },
    "adjustments":     { "currency": "INR", "value":  -2000 },
    "emi":             { "currency": "INR", "value":  30000 },
    "total_due":       { "currency": "INR", "value": 133000 },
    "cleared":         { "currency": "INR", "value": 120000 },
    "closing_balance": { "currency": "INR", "value":  13000 }
  }
}
```

`entries[]` reuses the existing `LedgerResponse`/`entryToResponse(e, currency)`
(amount as `Money`, plus `entry_type`, `direction`, `chore_id`, `note`, `period`,
`created_at`) — the per-member month passbook the member statement screen (§5)
needs, without a second call. Ordered `created_at` ASC.

### 3.7 Status codes

| Code | When |
|---|---|
| 200 | success (including empty `members` for a member's pre-join month) |
| 400 | bad group UUID, malformed `period`, malformed `user_id` |
| 401 | not authenticated |
| 403 | caller not a group member; member requesting another member's `user_id` |
| 500 | posting failure / DB error |

## 4. Edge cases (each → a named test in §6)

1. **Empty month** (member joined earlier, no entries in M): `opening = closing`
   (pure carryover), all five figures 0, `entries: []`, **row present**.
   → `TestCompute_EmptyMonth_OpeningEqualsClosing`.
2. **First-ever month** (M == join month, no prior entries): `opening == 0` in the
   group currency; `closing == earned − cleared`.
   → `TestCompute_FirstMonth_OpeningZero`.
3. **Pre-join month** (M < join month): member absent from admin view; member's
   own query → `members: []`, 200 (distinct from empty month: **no row**).
   → `TestStatement_MidMonthJoinFlooring` (integration).
4. **Only some entry types present** (e.g. base + payment, no chores/emi/adj):
   absent categories are 0; math still balances.
   → `TestCompute_PartialTypes`.
5. **Signed adjustment** (a debit adjustment): `adjustments.value < 0`, reduces
   `total_due`.
   → `TestCompute_AdjustmentSigns`.
6. **Loan final-partial-EMI month** (§3.6/D5: last installment = min(emi,
   outstanding)): the smaller final `emi_debit` posts in its month; `emi(M)`
   reflects the partial amount; closing carries correctly into the (now
   loan-free) next month.
   → `TestStatement_LoanFinalPartialEMI` (integration).
7. **Month boundary / timezone**: a manual entry at `YYYY-MM-last 23:59` local vs
   `next-01 00:00` local land in different months; `effMonth` uses `.Local()`.
   → `TestEffMonth_BoundaryAndTZ` (unit).
8. **Multi-currency isolation** (D7): the statement's currency is exactly
   `groups.currency`; every `Money` in the response carries it; no sum ever mixes
   currencies (each group has one currency, and the endpoint reads a single
   group). → `TestStatement_CurrencyFromGroupOnly` (integration; EUR + INR groups
   assert per-group currency, no bleed).
9. **Future month** (M > current server month): `PostDue` only materializes up to
   the current month, so a future M shows `opening == closing == current balance`
   with `earned == cleared == 0` and `entries: []`. Documented behavior (the UI
   never navigates past the current month); the invariant still holds.
   → `TestCompute_FutureMonthProjectsBalance`.

### 5.2 New components (add near `BalanceResponse`, ~line 2129)

- **`StatementResponse`**: `group_id` (uuid), `period` (string `^\d{4}-\d{2}$`),
  `currency` (enum `[EUR,USD,INR]`), `members` (array of
  `MemberStatementResponse`), `group_total` (`StatementTotals`, `nullable: true`
  — omitted for member callers / narrowed admin views). Required: `group_id`,
  `period`, `currency`, `members`.
- **`MemberStatementResponse`**: `user_id` (uuid), `name` (string), and the eight
  money fields `opening_balance`, `base`, `chores`, `adjustments`, `emi`,
  `total_due`, `cleared`, `closing_balance` — each `allOf: [$ref Money]`; plus
  `entries` (array of `LedgerResponse`). Descriptions must state which fields are
  signed (`opening_balance`, `adjustments`, `total_due`, `closing_balance`) vs
  non-negative (`base`, `chores`, `emi`, `cleared`), and that `closing_balance`
  equals next month's `opening_balance`. All fields required except `entries`
  optional-but-always-present.
- **`StatementTotals`**: the same eight money fields (no `user_id`/`name`/
  `entries`), all `allOf: [$ref Money]`, all required. Reused by `group_total`.

Reuse the existing `Money`, `LedgerResponse`, `ErrorResponse` components verbatim
— do not add a second money shape (§9.6).

- `TestCompute_FirstMonth_OpeningZero` — no prior entries ⇒ `Opening == 0`.
- `TestCompute_PartialTypes` — subsets of types; absent categories 0.
- `TestCompute_AdjustmentSigns` — credit vs debit adjustment sign into `Adjustments`/`TotalDue`.
- `TestCompute_FutureMonthProjectsBalance` — M after all entries ⇒ `Opening==Closing`, figures 0, `Entries` empty.
- `TestCompute_ExcludesNonApproved` — pending/rejected entries never counted.
- `TestCompute_EntriesOrderedAsc` — `Entries` sorted `created_at` ASC, only `effMonth==M`.
- `TestEffMonth_SystemUsesPeriod` — `Period` wins when set.
- `TestEffMonth_BoundaryAndTZ` — manual entry `created_at` bucketed by `.Local()` month; last-second-of-month vs first-second-of-next land in different months.
