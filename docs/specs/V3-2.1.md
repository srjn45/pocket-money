### `014_identity_shadow_users.up.sql`

```sql
-- V3-2.1: shadow users (nullable password + status + claimed_at) and the
-- notifications table (§3.1, §3.7). notifications is INSERT-ONLY in this WP;
-- the list/unread/mark-read READ API is Phase 5 (V3-5.1).

-- password_hash becomes NULLABLE. NULL ⇔ shadow user (cannot authenticate).
-- DROP NOT NULL is idempotent (no-op if already nullable).
ALTER TABLE users ALTER COLUMN password_hash DROP NOT NULL;

-- status: 'shadow' | 'registered'. Existing rows backfill to 'registered' via
-- the DEFAULT (they all have a password already). Keep the DEFAULT: 'registered'
-- is the safe common case and existing INSERTs that omit status stay correct;
-- shadow creation sets status explicitly.
ALTER TABLE users
    ADD COLUMN IF NOT EXISTS status text NOT NULL DEFAULT 'registered'
        CHECK (status IN ('shadow', 'registered'));

-- when a shadow row was claimed by registration (§3.1). NULL for never-claimed.
ALTER TABLE users
    ADD COLUMN IF NOT EXISTS claimed_at timestamptz NULL;

-- In-app notifications (§3.7). INSERT-ONLY here; read API is Phase 5.
CREATE TABLE IF NOT EXISTS notifications (
    id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    type       text NOT NULL,
    payload    jsonb NOT NULL DEFAULT '{}',
    read_at    timestamptz NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

-- Read API (Phase 5) will page a user's notifications newest-first; index now.
CREATE INDEX IF NOT EXISTS idx_notifications_user_created
    ON notifications (user_id, created_at DESC);
```

### `014_identity_shadow_users.down.sql`

```sql
-- Reverse of 014. DROP COLUMN cascades the inline CHECK on status.
DROP INDEX IF EXISTS idx_notifications_user_created;
DROP TABLE IF EXISTS notifications;

ALTER TABLE users DROP COLUMN IF EXISTS claimed_at;
ALTER TABLE users DROP COLUMN IF EXISTS status;

-- Restore the original NOT NULL. This is a dev/test teardown path
-- (TestMigrations_UpAndDown rolls the whole chain down on an empty DB); it
-- assumes no shadow rows (password_hash NULL) remain, which holds there.
ALTER TABLE users ALTER COLUMN password_hash SET NOT NULL;
```

**Why DEFAULT stays on `status` (unlike `013`'s currency):** `013` dropped its
default to force every group insert to state a currency. Here `'registered'` is
the correct default for every non-shadow insert, and the only inserts that must
differ (shadow creation) set `status` explicitly — so keeping the default is
both safe and less churn on existing `INSERT`s.

### 2.1 NEW path — `POST /api/v1/groups/{id}/members`

Add under the existing `/api/v1/groups/{id}/members` path item (which currently
has only `get`). Add a `post`:

- **Summary:** Add a member by email (add-by-email lifecycle, §3.1). Head-only.
- **Security:** `BearerAuth`.
- **Path param:** `id` (uuid).
- **Request body (required):** `$ref: AddMemberRequest`.
- **Responses:**

  - `409` — the target email is **already a member of this group** (duplicate
    add); `ErrorResponse`. See §4.4 for the idempotency contract.
  - `500` — `ErrorResponse`.

### 3.3 `UserRepo` (`internal/db/user_repo.go`)

1. **`Create` — unchanged signature**, but set `status='registered'` explicitly
   and return the new fields. Keeping the `(email, passwordHash string, name,
   dob, sex)` signature means **every existing caller and test compiles
   unchanged** (they pass a real hash string). Set the struct's `PasswordHash`
   to `&passwordHash`, `Status = UserStatusRegistered`.

   ```sql
   INSERT INTO users (id, email, password_hash, name, status, dob, sex)
   VALUES ($1, $2, $3, $4, 'registered', $5, $6)
   RETURNING created_at
   ```

2. **`GetByID` / `GetByEmail` — scan the new columns.** Both now select
   `password_hash, status, claimed_at` and scan `password_hash` into the
   `*string` field and `claimed_at` into `*time.Time`:

   ```sql
   SELECT id, email, password_hash, name, status, claimed_at, dob, sex, created_at
   FROM users WHERE id = $1   -- (email = $1 for GetByEmail)
   ```

   Scan order: `&user.ID, &user.Email, &user.PasswordHash, &user.Name,
   &user.Status, &user.ClaimedAt, &user.DOB, &user.Sex, &user.CreatedAt`.

3. **NEW `CreateShadow(ctx, q Querier, email, name string) (*models.User, error)`**
   — creates a shadow user (no password). Takes a `Querier` so it runs inside
   the add-by-email transaction (§4). Returns `ErrDuplicateEmail` on the unique
   violation (defensive; the caller already checked).

   ```sql
   INSERT INTO users (id, email, password_hash, name, status)
   VALUES ($1, $2, NULL, $3, 'shadow')
   RETURNING created_at
   ```

   Set `PasswordHash = nil`, `Status = UserStatusShadow` on the returned struct.

4. **NEW `GetByEmailForUpdate(ctx, q Querier, email string) (*models.User, error)`**
   — same select as `GetByEmail` but `... WHERE email = $1 FOR UPDATE`, run on
   the tx `Querier`. Locks the row so a concurrent register-claim can't race the
   add. `ErrNotFound` when absent.

5. **NEW `ClaimShadow(ctx, q Querier, userID uuid.UUID, passwordHash string) error`**
   — upgrades a shadow row **in place** (same id):

   ```sql
   UPDATE users
   SET password_hash = $2, status = 'registered', claimed_at = now()
   WHERE id = $1 AND status = 'shadow'
   ```

   Return `ErrNotFound` if `RowsAffected() == 0` (already claimed / not a
   shadow) so the caller can fall through to the duplicate-email path safely.

### 3.4 Auth compare sites (`internal/handlers/auth.go`)

`PasswordHash` is now `*string`. Two readers, both must first reject a nil
(shadow) hash — this is the **exact rejection point** for §5:

- **`Login`** (after `GetByEmail`): if `user.PasswordHash == nil` (equivalently
  `user.Status == models.UserStatusShadow`), return
  `401 {"error":"invalid email or password"}` — the **same generic message** as a
  wrong password, to avoid revealing that the email exists as a shadow. Only when
  non-nil, `bcrypt.CompareHashAndPassword([]byte(*user.PasswordHash), ...)`.
- **`ChangePassword`** (after `GetByID`): a shadow can never hold a token, so
  this is defensive — if `user.PasswordHash == nil`, return `401 {"error":"not
  authenticated"}`. Otherwise deref as above.

### 3.5 NEW `NotificationRepo` (`internal/db/notification_repo.go`) — insert-only

```go
type NotificationRepo struct{ pool *pgxpool.Pool }

func NewNotificationRepo(pool *pgxpool.Pool) *NotificationRepo { ... }

// Insert writes one notification. q lets it join the caller's transaction so the
// notification is atomic with the membership/claim change. payload is a JSON
// object (marshaled by the caller). INSERT-ONLY — no read methods in this WP.
func (r *NotificationRepo) Insert(ctx context.Context, q Querier,
	userID uuid.UUID, ntype string, payload []byte) error {
	_, err := q.Exec(ctx,
		`INSERT INTO notifications (user_id, type, payload) VALUES ($1, $2, $3)`,
		userID, ntype, payload)
	return err
}
```

## 4. Handler — `POST /groups/{id}/members` (add-by-email lifecycle, §3.1)

New method `AddMemberByEmail` on `GroupHandler` (`internal/handlers/groups.go`).
`GroupHandler` gains a `notificationRepo *db.NotificationRepo` and a
`userRepo *db.UserRepo` dependency (add to the struct + `NewGroupHandler`
signature; wire in `cmd/server/main.go`).

Request struct (mirror `AddMemberRequest`):

```go
type AddMemberRequest struct {
	Email string `json:"email" binding:"required,email"`
	Name  string `json:"name"  binding:"required"`
}
```

Flow:

1. Auth: `auth.GetUserID` → 401 if absent. Parse `:id` → 400 on bad uuid.
2. Bind `AddMemberRequest` → 400 on error.
3. **Authorization:** `groupRepo.GetMember(groupID, callerID)`; `ErrNotFound`
   → 403 "not a member of this group"; if `member.Role != models.RoleHead` →
   403 "only the group head can add members". (Matches `CreateInvite`'s pattern.)
4. Begin a tx on `h.pool` (`defer tx.Rollback`).
5. **Resolve the user by email** with `userRepo.GetByEmailForUpdate(ctx, tx, email)`:
   - **`ErrNotFound` → create a shadow** (§3.1 case 3):
     `user = userRepo.CreateShadow(ctx, tx, email, req.Name)`. `notify = false`.
   - **Found, `status == registered`** (§3.1 case 2): use it. `notify = true`
     (N-1).
   - **Found, `status == shadow`** (§3.1 case 4): use it. `notify = false`
     (shadow can't read a notification).
6. **Attach:** `groupRepo.AddMemberTx(ctx, tx, groupID, user.ID, models.RoleMember)`.
   - On `ErrDuplicateMember` → **rollback, 409** "user is already a member of
     this group" (§4.4). No notification, no user mutation persists (the shadow
     create, if any, rolls back — but a duplicate implies the user already
     existed, so nothing is lost).
7. **N-1 insert** (only when `notify == true`): build the payload and
   `notificationRepo.Insert(ctx, tx, user.ID, models.NotificationAddedToGroup, payload)`.
   Payload (JSON object):

   ```json
   { "group_id": "<uuid>", "group_name": "<name>", "added_by_user_id": "<caller uuid>" }
   ```

   (Fetch `group.Name` via `groupRepo.GetByID`, or pass it through — either is
   fine; keep it inside the tx.)
8. **Commit.** On commit error → 500.
9. **Respond `201`** with `MemberResponse{ UserID: user.ID, Name: user.Name,
   Email: user.Email, Role: models.RoleMember, Status: user.Status,
   JoinedAt: <from AddMemberTx> }`.

Register the route in `cmd/server/main.go` next to the existing member routes:

```go
protected.POST("/groups/:id/members", groupHandler.AddMemberByEmail)
```

### 4.1–4.4 Lifecycle branches (restated for the test map)

- **4.1 Registered match →** attach as `member`, insert **N-1** to that user.
- **4.2 No user →** create shadow (`password_hash NULL`, `status 'shadow'`,
  `name` from request), attach as `member`, **no notification**.
- **4.3 Existing shadow →** attach to this group only, **no notification**, **no
  new user row**, id unchanged.
- **4.4 Duplicate add (already a member of THIS group) →** **`409 Conflict`**,
  human-readable error, **no second membership row and no second N-1**. This is
  the chosen idempotency contract: repeated adds leave the system in one stable
  state (exactly one membership, at most one N-1 from the first successful add).
  `409` (not `200`) is chosen for an explicit signal and to match the codebase
  idiom (`RemoveMember` uses `409` for membership-state conflicts). **Tests must
  assert `409`.**

## 5. Register-claim logic (`internal/handlers/auth.go`, `Register`)

Rewrite `Register` so a matching **shadow** is claimed in place instead of
being a duplicate-email error:

1. Hash the password (unchanged).
2. `existing, err := userRepo.GetByEmail(email)`:
   - **`ErrNotFound`** → create a brand-new registered user
     (`userRepo.Create`, existing path), issue token, `201` with token+user
     (`status` = `registered`). **No notification** (fresh account, no groups).
   - **Found, `status == registered`** → `400 {"error":"email already exists"}`
     (unchanged behavior for a real duplicate).
   - **Found, `status == shadow`** → **CLAIM** (steps 3–5).
3. **Claim in a transaction** (`h.pool.Begin`):
   a. `userRepo.GetByEmailForUpdate(ctx, tx, email)` to lock the row; re-check
      `status == shadow` (guards a concurrent claim — if it flipped to
      registered, treat as `400 email already exists`).
   b. `userRepo.ClaimShadow(ctx, tx, existing.ID, hash)` — sets password,
      `status='registered'`, `claimed_at=now()`. **Same user id** ⇒ every
      membership/ledger/loan/allowance stays attached automatically.
   c. **N-2 fan-out:** find the user's groups
      (`groupRepo` — a `ListGroupIDsForUser(ctx, tx, userID)` helper, or reuse
      an existing membership query), and for each group,
      `groupRepo.ListHeadUserIDs(ctx, tx, groupID)`; for each head user id
      **that is not the claimant themselves**, insert **N-2**
      (`NotificationShadowClaimed`) with payload:

      ```json
      { "group_id": "<uuid>", "group_name": "<name>",
        "claimed_user_id": "<uuid>", "claimed_user_name": "<name>",
        "claimed_user_email": "<email>" }
      ```
   d. Commit. On error → 500.
4. Issue a JWT for `existing.ID` (auto-login, same as a fresh register).
5. Respond `201` with `LoginResponse{token, user}` where `user.status ==
   registered`.

**Add `GroupRepo.ListGroupIDsForUser(ctx, q Querier, userID) ([]uuid.UUID, error)`**
(`SELECT group_id FROM group_members WHERE user_id = $1`) if no existing tx-safe
equivalent — used only by the claim fan-out.

**MVP security stance (§3.1):** email is unverified, so claiming is trust-based;
the N-2 notification to admins is the mitigation and this is a family app. Do
**not** add email verification here (post-MVP). Just implement the claim + N-2.

## 6. Shadow users CANNOT authenticate (§5 of the WP prompt)

The single source of truth is **`Login` rejecting `password_hash IS NULL`**
(§3.4): a shadow has `PasswordHash == nil`, so the compare is skipped and `401`
"invalid email or password" is returned (generic message, no enumeration).
Token issuance (`auth.IssueToken`) is reached **only** on the Login success path
and the Register success/claim path — a shadow reaches neither (Login rejects
it; Register *upgrades* it to registered before issuing), so **no token is ever
minted for a `status='shadow'` / `password_hash IS NULL` user.** No change to
`internal/auth/jwt.go` is needed; the guarantee is structural. State this
explicitly in the PR description so review can verify the invariant.
