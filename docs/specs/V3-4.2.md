## 0. Summary

Two screens are rebuilt on the already-shipped statement API:

1. **Group home = the monthly Statement** (`app/app/(app)/groups/[id]/index.tsx`,
   replacing the current members-list / balance overview). Admin: one row per
   non-admin member with `payable · paid · remaining`, a group-total headline, a
   month switcher, and a **Record payment** button per row pre-filled with that
   member's remaining. Member: the same screen scoped to their own single row,
   read-only, headlined "You'll receive …".
2. **Dashboard v3** (`app/app/(app)/index.tsx`): "Groups you manage" / "Groups
   you're in" sections with a per-group current-month headline **in the group's
   own currency** (D7, never summed).

which the endpoint already role-scopes (admin → all rows + `group_total`; member
→ own row, no total) and stamps with the group's currency. Recording a payment
is a `POST /groups/{id}/ledger` with `entry_type: "settlement"`; invalidating the
statement query afterward recomputes `remaining → 0`.

## 1. The exact API contract this screen consumes

### 1.1 `GET /api/v1/groups/{id}/statement?period=YYYY-MM` → `StatementResponse`

Fields consumed (from `api-types.gen.ts`, verified):

```
StatementResponse {
  group_id: string
  period:   string          // "YYYY-MM"
  currency: "EUR"|"USD"|"INR"
  members:  MemberStatementResponse[]   // admin: all non-admin members; member: [self] or []
  group_total?: StatementTotals | null  // admin unfiltered only; null for member
}
MemberStatementResponse {
  user_id, name
  opening_balance  Money   // signed  (carryover)
  base             Money   // ≥0
  chores           Money   // ≥0
  adjustments      Money   // signed
  emi              Money   // ≥0
  total_due        Money   // signed = opening+base+chores+adjustments−emi
  cleared          Money   // ≥0  (payments this month)
  closing_balance  Money   // signed = total_due−cleared  (== next month's opening)
  entries?         LedgerResponse[]   // month passbook, created_at ASC
}
StatementTotals { the same 8 Money fields, no user_id/name/entries }
```

Every `Money.currency == StatementResponse.currency == group's currency` (D7).
`value` is int64 **minor units** — render only through `AmountText`
(`minorUnits`/`currency` props), never format by hand.

### 1.2 The `payable · paid · remaining` mapping (⚠ reconciliation — read this)

§5 writes the row as `base + chores − EMI = payable · cleared · remaining`. That
is the **compact label**, not the full arithmetic. The API's authoritative
figures are `total_due` and `closing_balance`, which also fold in
`opening_balance` (prior-month carryover, D1) and `adjustments`. For the
displayed row to reconcile (`payable − paid == remaining`) **and** for
"record payment → remaining 0" to hold, the mapping **must** be:

| Screen label | API field | Note |
|---|---|---|
| base | `base` | ≥0 |
| chores | `chores` | ≥0 |
| − EMI | `emi` | ≥0 magnitude, shown subtracting |
| (carried) | `opening_balance` | **surface it** — else payable≠opening+earned |
| (± adjust) | `adjustments` | **surface it** — signed, folds into total_due |
| **= payable** | **`total_due`** | = opening+base+chores+adjustments−emi |
| **· paid** | **`cleared`** | payments recorded this month |
| **· remaining** | **`closing_balance`** | = total_due−cleared; pre-fills Record-payment |

The Record-payment button pre-fills **`closing_balance`** (the remaining). Paying
exactly that amount adds a `settlement` debit of `closing_balance`, so
`cleared += closing_balance` and the recomputed `closing_balance → 0` — the
acceptance criterion. Surfacing `opening_balance` and `adjustments` in the row
(even if de-emphasized) is required so the row's own math is internally
consistent; showing only `base + chores − emi` as "payable" would visibly fail
`payable − paid = remaining` whenever carryover or an adjustment exists.
**FLAG:** this reconciliation is a spec inference, not spelled out in §5 — but it
is forced by the invariant and the acceptance flow; IMPL must not display a
"payable" that excludes `opening_balance`/`adjustments`.

### 1.3 Record payment = `POST /api/v1/groups/{id}/ledger` (settlement)

```
CreateLedgerRequest {
  entry_type: "settlement"          // D9 "payment"; server sets direction=debit
  user_id:    <the row's member>    // admin may target any member
  amount:     { currency, value }   // currency = group's (D7); value = remaining minor units
  note?:      string
}
```

Reuse `ledgerApi.create` / `useCreateLedgerEntry` (existing). **Currency is the
group's** — take it from `StatementResponse.currency` (equivalently
`group.currency`); never let the client choose one (D7; server rejects a
mismatch 400). No new endpoint, no PUT (so the known CORS-on-PUT gotcha is not
reintroduced).

## 2. STATEMENT SCREEN — admin

Route: `app/app/(app)/groups/[id]/index.tsx` (the group Overview section; keeps

### 2.1 Data flow

- `const { id } = useLocalSearchParams<{ id: string }>()` — group id from the
  route (already resolves for this index route; e2e reaches it via `page.goto`).
- `const [period, setPeriod] = useState(currentPeriod())` — `"YYYY-MM"` **local
  state, NOT a route param** (deliberate: keeps the expo-router web-param gotcha
  off the statement fetch — only `id` comes from the URL, `period` never does).
- `const stmt = useStatement(id, period)` → `useQuery({ queryKey:
  qk.statement(id, period), queryFn: () => statementApi.get(id, period),
  enabled: !!id })`. The endpoint triggers `PostDue`, so opening the statement
  materializes the current month's allowance/EMI (dashboard does not — see §4.2).
- Role: derive from `useGroup(id)` members (`role === 'admin'`), same as today;
  OR simpler — the endpoint returns `group_total != null` **iff** the caller is
  an unfiltered admin, so `stmt.data.group_total` presence already discriminates
  the admin view. Use the group role for layout choice (matches existing code),
  and `group_total` for the total block.

### 2.2 Layout (top → bottom)

1. `<GroupSectionTabs active="overview" />` (unchanged).
2. **Month switcher** — `MonthHeader` extended with prev/next controls
   (§5.1). `‹` sets `period = prevPeriod(period)`; `›` sets `period =
   nextPeriod(period)` and is **disabled when `period === currentPeriod()`** (the
   UI never navigates into a future month — V3-3.1 §4 edge 9; a future statement
   is a meaningless projection). Right slot shows the **group total remaining** =
   `group_total.closing_balance` via `AmountText` (currency from `stmt.currency`).
3. **Group total headline** (`testID="statement-group-total"`) — "Remaining to
   pay this month" with `AmountText(group_total.closing_balance)`; optionally
   `payable`/`paid` subfigures from `group_total.total_due`/`cleared`. Only when
   `group_total` present (admin, unfiltered).
4. **Add entry** button (`testID="statement-add-entry"`) → opens the existing
   `AddEntrySheet` (`mode="head"`, `members={nonAdminMembers}`,
   `chores={choresQuery.data}`, `currency={stmt.currency}`) — the acceptance
   "add chore entry" affordance. (Today's admin "Add entry" button has **no**
   testID; add one.)
5. **Member rows** — `FlatList` over `stmt.members`, each a **`StatementRow`**
   (§4). Empty → `EmptyState` under `testID="statement-empty"`.

### 2.3 StatementRow (admin) — per member

- Root pressable `testID={`member-card-${m.user_id}`}` → drills into member
  detail (`/(app)/groups/${id}/members/${m.user_id}`), preserving the existing
  admin→member-detail flow. **testID kept as `member-card-*` on purpose** — see
  §5.2.
- Shadow badge preserved: render `member-shadow-badge-${m.user_id}` when the
  member's `status === 'shadow'` (member `status` comes from `useGroup`
  members, joined to the statement row by `user_id`; the statement API has no
  `status` field). onboarding T3 depends on this badge.
- Figures (via `AmountText`, currency = `stmt.currency`):
  `base` · `chores` · `−emi` → **payable** (`total_due`,
  `testID={`statement-payable-${uid}`}`) · **paid** (`cleared`,
  `testID={`statement-cleared-${uid}`}`) · **remaining** (`closing_balance`,
  `testID={`statement-remaining-${uid}`}`). Surface `opening_balance` and
  `adjustments` (de-emphasized) per §1.2.
- **Record payment** button `testID={`statement-record-payment-${uid}`}`, shown
  **only when `period === currentPeriod()`** (see §2.4). `onPress` opens
  `RecordPaymentSheet` (§4.3) pre-filled with `closing_balance`. Its touch must
  not propagate to the row's drill-in press (separate `Pressable`, or
  `stopPropagation`).

### 2.4 ⚠ Record-payment only on the current month (FLAG — spec decision)

A `settlement` entry is created with `created_at = now`, so it always lands in
the **current** month's `cleared` regardless of which `period` is on screen.
Showing "Record payment" while viewing a past month would let an admin pay
against a historical row yet see the payment appear in *this* month — confusing
and wrong. §5 frames payment as a **this-month** action ("Past months = the
audit archive"). **Decision:** render the Record-payment button and the
group-total "remaining to pay this month" affordances **only when `period ==
currentPeriod()`**; past months are read-only archive. This is not explicitly in
§5 — flagged; it is the only interpretation consistent with the settlement
created-at semantics.

### 2.5 Refetch / invalidation after a payment

`RecordPaymentSheet` uses `useCreateLedgerEntry(groupId)`. Its `onSuccess`
already invalidates `qk.ledger`/`qk.balance`/`qk.group`; **this WP adds
`qk.statement(groupId)` to that invalidation** (`useInvalidateGroup` in
`hooks/useLedger.ts`) so the open statement refetches and `remaining` recomputes
to 0. `qk.statement(groupId)` (prefix, no period) invalidates **all** cached
months for the group. Also add `qk.groups()` invalidation on payment is not
required for the statement screen, but the dashboard headline (§4) reads
`summary_balance` from `qk.groups()` — invalidate `qk.groups()` too so the
dashboard number tracks (cheap; see §4.2).

## 4. DASHBOARD v3

Route: `app/app/(app)/index.tsx`. The current screen already renders the two
sections and per-group figures from `GroupSummaryResponse.summary_balance`. This
WP is a **copy/semantics pass**, not a data-source change.

### 4.1 Data source for the per-group headline (cited)

**`GroupSummaryResponse.summary_balance`** from **`GET /api/v1/groups`**
(`groupsApi.list` → `useGroups`). Per `openapi.yaml`/`api-types.gen.ts`, that
field is already:
- **role-scoped** — admin: "the sum of all NON-admin members' balances (= total
  the admin owes members)"; member: "the caller's OWN balance in this group".
- **per-group currency** — a `Money` stamped with the group's own currency (D7).
- **never summed across groups** — one value per group card; the dashboard shows
  them side by side, never a cross-group total (D7).

This equals the current-month **remaining** (§5 headline): `summary_balance =
Σ approved credits − Σ approved debits = closing_balance` of the current month
(nothing is future-dated, so `effMonth ≤ current` for every entry). So the
existing single `GET /groups` call is the correct, cheapest source. **Do NOT add
a per-group `GET /statement` fan-out on the dashboard** — it would be N calls,
reintroduce the web-param concern per card, and risk a D7 cross-currency
summing mistake. Cite: `GroupSummaryResponse.summary_balance` description in
`backend/openapi.yaml` (component `GroupSummaryResponse`).

### 4.2 ⚠ Dashboard-vs-statement consistency (FLAG — accepted BE behavior)

`GET /groups` **deliberately does not trigger `PostDue`**
(`backend/internal/handlers/groups.go:188` — "Does NOT trigger posting"), whereas
the statement endpoint does. So on the 1st of a month, before the group is
opened, the dashboard headline can lag the current month's not-yet-posted
allowance/EMI; it self-heals the moment the user opens the group (statement runs
`PostDue`) and this WP invalidates `qk.groups()` on payment. This is an accepted
BE design choice, **out of scope for this FE WP** — flagged, not fixed. Do not
try to force-post from the dashboard.

### 4.3 Copy / rendering changes (this WP)

- Section titles already read "Groups You Manage" / "Groups You're In" (≈ §5
  "Groups you manage" / "Groups you're in") — keep.
- Admin card caption: change **"owed to members"** → **"remaining to pay this
  month"** (§5 headline framing) via `AmountText(summary_balance)` (neutral/
  credit tone as today).
- Member card: keep `AmountText(summary_balance)`; caption **"to receive this
  month"** (positive) matching §5 "to-receive". Tone: credit when ≥0.
- No structural change; `group-card-${id}`, `dashboard-root`, `dashboard-empty`,
  `dashboard-create-group` testIDs preserved.
