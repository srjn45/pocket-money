## 1. Member detail / Passbook screen

**Route (existing, extended):** `app/app/(app)/groups/[id]/members/[userId].tsx`
(root `testID="member-detail-root"`, reached from the statement `member-card-${uid}`
via `router.push({ pathname: '/(app)/groups/${gid}/members/${uid}', params:{name} })`).

This screen already renders balance header, allowance summary, an inline read-only
loans block, an Add-entry button, and the member's `LedgerList`. V3-4.3 turns it into
the **passbook**: passbook ledger (reused) + **base-amount history** section + **loan
cards** (extracted to `LoanCard`, tappable → loan detail) + **corrections** affordance
on manual rows.

### 1.1 Web-param handling (GOTCHA — call out explicitly)

`members/[userId]` is keyed on **two** dynamic segments: the parent `[id]` (group) and
the child `[userId]`. Both come from the URL:

```ts
const { id, userId, name } = useLocalSearchParams<{ id: string; userId?: string; name?: string }>();
const gid = id ?? '';
const uid = userId ?? '';
```

- **Never** derive `userId` from anything but `useLocalSearchParams`; never rely on a
  sibling-link click to populate it (the expo-router web-param gotcha — a `<Link>` to a
  sibling route does **not** repopulate a parent dynamic segment on web, so
  group-scoped queries would fetch `/groups//…`). The existing statement-row `push`
  passes a full `pathname` with both ids interpolated, so both segments resolve. Keep
  that call shape; do **not** switch it to relative navigation.
- Guard every hook with `enabled: !!gid` / scope by `uid` — `useLedger(gid, {user_id: uid})`,
  `useLoans(gid)` filtered client-side to `uid`, `useAllowances(gid)` filtered to `uid`.
  All already gate on `!!groupId`.
- `name` is a display-only param (may be absent on a hard reload / deep link); title
  falls back to "Ledger". Do not block rendering on `name`.

### 1.2 Data flow

| Section | Hook / endpoint | Notes |
|---|---|---|
| Balance header | `useBalance(gid)` → `GET /groups/{id}/balance`, `.find(b=>b.user_id===uid)` | reused as-is |
| Base-amount history | `useAllowances(gid)` → `GET /groups/{id}/allowances`, filter `a.user_id===uid` | **new section** (all history rows, not just current/upcoming) |
| Passbook ledger | `useLedger(gid, { user_id: uid })` → `GET /groups/{id}/ledger?user_id={uid}` | reused `LedgerList` |
| Loan cards | `useLoans(gid)` → `GET /groups/{id}/loans`, filter `l.user_id===uid` | extracted to `LoanCard` |
| Chores (for row titles + Add-entry picker) | `useChores(gid)` | reused |
| Group / role / currency | `useGroup(gid)` | admin-only screen (member is redirected to overview — existing `if (!isHead) <Redirect/>`) |

**Currency = group currency (D7):** `const currency = group?.currency ?? 'INR'`. Every
amount rendered through `AmountText`/`formatMoney` with that currency. No hardcoded
`₹/€/$` (the `currencySymbol(currency)` helper is the only place a symbol is chosen,
inside confirm copy). This screen is **admin-only** (member's own passbook lives on the
group-home member view, §index.tsx MEMBER VIEW — unchanged).

### 1.3 Layout (top → bottom)

1. **Balance header** (existing) — name, shadow badge (`member-detail-shadow-badge`),
   balance `AmountText`, hint, `AllowanceSummary` (keeps `member-allowance-button`).
2. **Add-entry button** (existing `member-add-entry-button`) → opens `AddEntrySheet`
   in `mode="head"` with `fixedUserId={uid}` (now 4-type — §3).
3. **Base-amount history** (NEW `PassbookBaseHistory` block, `testID="base-history"`)

   month (`humanMonthFull(effective_from)`) + `AmountText(amount)` (value 0 → "Paused"

4. **Loans** (existing section header + "Manage in Loans tab"), rendering `LoanCard`
   per active/requested loan (§2). Hidden when none / on loans error.
5. **Passbook** = `LedgerList` (existing) with `loans={memberLoans}` passed so EMI rows
   title as "EMI k/n", and **corrections** enabled (`canEdit={isHead}`, §4).

Keep the "all hooks before any early return" ordering (§9.3) already in the file.

## 2. Loan card + Loan detail (repayment schedule)

### 2.1 Data reality (GOTCHA — schedule is DERIVED, not returned)

`GET /groups/{id}/loans` (and there is **no** loan-by-id GET; the list is the source)
returns `LoanResponse`:

```
id, group_id, user_id,
principal:Money, installments:int, emi_amount:Money (= ceil(principal/installments)),
start_period:string|null ('YYYY-MM', null until active),
status:'requested'|'active'|'rejected'|'closed',
note, requested_at, decided_by, decided_at,
installments_posted:int (count of posted EMI entries),
outstanding:Money (principal − Σ posted EMIs)
```

There is **no `repaid` field and no `schedule` array.** Both are computed FE-side from
the primitives — a pure helper `buildLoanSchedule(loan)` (new, in `app/src/loan-format.ts`):

- **repaid** = `principal.value − outstanding.value`.
- **installment i (1-based, i = 1..installments):**
  - `due_period` = `addMonths(start_period, i-1)` (skip if `start_period` null → loan
    not yet active → schedule shown as "starts once approved").
  - `amount` = `i < installments ? emi_amount.value : principal.value − emi_amount.value*(installments-1)`
    (the final installment is the remainder = `min(emi, outstanding)` at settlement — D5).
  - `status`: `i <= installments_posted` → **paid**; `i === installments_posted + 1` &&
    loan active → **due** (next up); else → **pending**. Closed loans → all remaining
    render **paid/closed**.
- Reuse `nextPeriod` (from `allowance-format.ts`) for month arithmetic; add a tiny
  `addMonths(period, n)` helper alongside `buildLoanSchedule` (loops `nextPeriod`).

`buildLoanSchedule` is unit-testable in isolation (see §7 tests) and drives both the
card progress affordance and the detail schedule list — the acceptance assertion
("loan card shows repaid/pending/schedule") reads its output.

### 2.2 `LoanCard` (NEW component, extracted from loans.tsx + member-detail)

`app/src/components/LoanCard.tsx`. Consolidates the two near-duplicate inline renderers
(`renderLoan` in `loans.tsx`, `renderLoanRow` in `members/[userId].tsx`). Props:
`{ loan, memberName?, currency, onPress?, actions? }`. Preserves the existing root
`testID={`loan-card-${loan.id}`}` (relied on by loans.spec / seeded-readonly).

Card body:
- Header: status badge (`loanStatusLabel/Tone`) + optional member name + `principal`.
- Note (italic) when present.
- **EMI progress affordance** (active/closed): `Outstanding`, `EMI ≈ x / month`,
  `Progress k/n paid`, plus a **repaid/pending line** →
  `Repaid <AmountText repaid/> · Pending <AmountText outstanding/>`
  (`testID={`loan-progress-${loan.id}`}` on the progress line so e2e can assert
  repaid/pending without brittle text scans).
- Requested: `Requested <principal> over n months`, `Est. EMI`.
- `onPress` (when given) → navigate to loan detail (§2.3); the whole card is a
  `Card onPress`. Action buttons (approve/reject/close) passed via `actions` slot so
  loans.tsx keeps admin controls; member-detail passes none (read-only).

### 2.3 Loan detail route (NEW — §5 "list + detail with repayment schedule")

**Route restructure:** convert `app/app/(app)/groups/[id]/loans.tsx` →
`app/app/(app)/groups/[id]/loans/index.tsx` (unchanged behaviour, list) and add

## 3. Add-entry type picker (single entry point, 4 types)

Extend **`AddEntrySheet`** (`app/src/components/AddEntrySheet.tsx`) from 3 → 4 types.
It stays the **one** add-entry entry point (opened from statement `statement-add-entry`,
member-detail `member-add-entry-button`, member overview `member-log-chore`).

### 3.1 Types, labels, endpoints

| Picker label (D9) | option `value` (UNCHANGED) | Creates | Endpoint / payload |
|---|---|---|---|
| Chore | `chore` | ledger row | `POST /groups/{id}/ledger` `{ entry_type:'chore', user_id?, chore_id }` (amount from chore config) |
| Payment | `settlement` | ledger row | `POST …/ledger` `{ entry_type:'settlement', user_id, amount:{currency,value}, note? }` |
| Adjustment | `adjustment` | ledger row | `POST …/ledger` `{ entry_type:'adjustment', user_id, amount, direction, note? }` |
| New loan | `loan` (NEW) | **loan ENTITY** | `POST /groups/{id}/loans` `{ user_id?, principal:{currency,value}, installments, note? }` |

> **CRITICAL — do not change existing option `value`s.** `e2e/support/pages.ts`
> `headAddEntry` calls `entry-type-picker.selectOption('settlement'|'adjustment')` by
> **value**. Only the **label** changes ("Settlement" → **"Payment"**). The `value`
> stays `settlement`. The new type adds `value='loan'`.

### 3.2 "New loan" branch (loan entity, not a ledger row)

- Fields when `kind==='loan'`: **Amount** (principal, reuse `entry-amount` field),
  **Repay over (months)** (`entry-loan-installments`, number-pad), optional **Note**.
  Show the derived `≈ EMI/month` hint (`Math.ceil(principal/installments)`), mirroring
  loans.tsx.
- Submit → new hook `useCreateLoan(gid)` (see §6) → `loansApi.request(gid, { user_id?,
  principal:{currency,value}, installments, note })`. In `mode==='head'` with
  `fixedUserId`, pass `user_id=fixedUserId` (admin creates a **pre-approved active**
  loan per `CreateLoanRequest`); in `mode==='member'` omit `user_id` (self request).
  `currency` is the group currency prop (D7) — never client-chosen.
- On success invalidate loans (+ ledger/balance/group/statement, since an admin-created
  active loan may post an immediate/next-period EMI). Toast "Loan added" / "Loan requested".
- **Member visibility:** currently the `mode==='head'` gate hides the type picker for
  members (members only log chores). Keep that — the 4-type picker is **admin (head)**;
  the member "Log a chore" flow is unchanged (chore-only). "New loan" for members stays
  on the Loans tab "Request Loan" (existing). So the picker gains "Payment"/"Adjustment"
  labels + the "New loan" option **in head mode only**. (Flag §10 if product wants
  member-initiated loan from this sheet — not required by §5/acceptance.)

### 3.3 `loansApi.request` signature extension

`loansApi.request` currently omits `user_id`. Extend to
`{ user_id?: string | null; principal; installments; note? }` (openapi `CreateLoanRequest`
already allows `user_id`). No new endpoint.

## 4. Corrections UI (D3) — edit/delete on MANUAL entries only

### 4.1 Editable vs system (source of truth)

The row decides from `entry.entry_type`:

```ts
const MANUAL_TYPES = new Set(['chore', 'settlement', 'adjustment']); // editable (admin)
// 'allowance', 'emi' → system, NOT editable (edit the base amount / loan instead)
const canCorrect = isHead && entry.status !== 'rejected' && MANUAL_TYPES.has(entry.entry_type);
```

Backend enforces the same (PUT/DELETE `/ledger/{id}` return 403 for `allowance`/`emi`
and for non-admin) — the UI just hides controls it must never offer. Member view
(`isHead=false`) shows **no** edit/delete affordance (D6).

### 4.2 Row affordance (`LedgerRow`)

Add to `LedgerRow` (props: `onEdit?`, `onDelete?`, `canCorrect?`). When `canCorrect`,
render a compact edit (pencil) + delete (trash) control in the row's right column
(reuse `Button variant="ghost" size="sm" icon`), with
`testID={`ledger-edit-${entry.id}`}` and `testID={`ledger-delete-${entry.id}`}`.
Pending manual entries keep their existing approve/reject controls; edit/delete are
additive and independent (an admin may correct an already-approved chore).

### 4.3 The "edited" affordance — **FLAG (contract gap), see §10.1**

`LedgerResponse` has **no `edited_at` / `updated` field**, and D3's `entry_audit` table
is deliberately **invisible** (V3-3.2 spec §"has no read API"). So a **persistent**
"edited" badge sourced from the entry cannot be built FE-only without a backend change,
which this WP forbids. Chosen behaviour for this WP:

- After a successful edit, show a **session-local** "Edited" `StatusBadge` (tone
  `neutral`) on that row (`testID={`ledger-edited-${entry.id}`}`), keyed by an in-memory
  `Set<entryId>` held on the passbook screen (survives refetch within the session via
  the set, cleared on unmount/reload). This satisfies the acceptance-flow assertion
  ("edit → badge shows") deterministically in one session without inventing an API
  field. It is **not** durable across reloads — flagged as a follow-up (§10.1) for a
  BE `edited_at` in a later WP if product wants persistence.

### 4.4 Edit sheet (reuse `AddEntrySheet` edit-mode)

Add an **edit mode** to `AddEntrySheet` (preferred over a separate component — the
amount/direction/note fields already exist). New props:
`mode` unchanged + `editEntry?: LedgerEntry`. When `editEntry` set:
- Title "Edit entry"; type picker **disabled/hidden** (type is immutable on edit —
  `EditLedgerRequest` only carries `amount`, `direction?`, `note?`).
- Prefill `amountStr` from `editEntry.amount`, `direction` from `editEntry.direction`,
  `note` from `editEntry.note`. **Chore edits:** `EditLedgerRequest` requires `amount`
  (value ≥ 1) even for a chore row, and forbids `direction` for chore/settlement — so
  the edit form shows the **amount** field for a chore correction (the acceptance flow
  edits a chore amount), hides direction for chore/settlement, shows direction for
  adjustment.
- Submit → `useEditLedgerEntry(gid).mutateAsync({ id: editEntry.id, amount:{currency,value},
  direction?, note? })` → `PUT /ledger/{id}`.

### 4.5 Delete

Trash → `confirmAsync` (destructive) → `useDeleteLedgerEntry(gid).mutateAsync(entry.id)`
→ `DELETE /ledger/{id}` (204). Toast "Entry deleted".

### 4.6 Invalidation (so statement + passbook update)

`useInvalidateGroup` (in `useLedger.ts`) already invalidates `ledger`, `balance`,
`group`, `statement` (prefix → all months), `groups`. **Reuse it** for the new
`useEditLedgerEntry` / `useDeleteLedgerEntry` `onSuccess`. This is exactly what makes the
acceptance flow work: edit a chore's amount on the passbook → statement `payable` /
`remaining` for that member recompute on the group-home refetch.

### 4.7 CORS (GOTCHA — verified clear)

`backend/internal/middleware/cors.go` already sets
`Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS`. Edit uses
**PUT `/ledger/{id}`**, delete uses **DELETE `/ledger/{id}`** — both already allowed
(V3-3.2 shipped the endpoints). No backend change; the new bit is only that the app now
*issues* PUT/DELETE from the correction UI. No action needed, but noted because the
correction UI is new.

## 5. Chores catalog restyle (reference data, not a primary tab)

**Route:** `app/app/(app)/groups/[id]/chores.tsx` (root `testID="chores-root"`).
It already shows `name`, `description` (as subtitle), amount, and a "System"/Variable
treatment. V3-4.3 restyle = **settings-like reference-data** presentation:

  amounts") and use `ListRow` with muted, settings-style rows (description always shown
  as the secondary line; amount right-aligned). Keep `chore-row-${id}`, `chores-add-button`,
  `chores-empty` testIDs.
- The `description` field is already wired through create/edit sheet + `ChoreResponse`
  — no API work. Ensure the description line renders even when short and reads as
  reference documentation (e.g., "What counts as done").

**"Not a primary tab" (§5) — FLAG, see §10.2.** Chores is currently one of three
`GroupSectionTabs` segments (Overview / Chores / Loans). §5 says chores should **not**
be a primary tab. Options:
- (A) **Keep the `/chores` route**, remove **Chores** from `GroupSectionTabs`, and add a
  secondary entry point (a "Manage chores" `ListRow`/gear link on the admin Overview,
  or from a group settings affordance). Route + testIDs preserved so
  `seeded-readonly` (`page.goto(/chores)`) and `openTab(page,'chores')` still work.
- (B) Leave the segmented control as-is (defer de-emphasis to V3-4.4 suite pass).

**Recommendation: (A)** — it is what §5 asks, low-risk because the route/testIDs are
untouched and e2e reaches `/chores` by full-URL nav, not by clicking the segment. If (A)
is taken, `GroupSectionTabs.SECTIONS` drops the `chores` entry (→ Overview / Loans) and
Overview gains a `chores-link` row (`testID="overview-chores-link"`) →

## 10. Flags (UX questions NOT settled by §5 / acceptance / D3·D5·D9)

### 10.1 "Edited" affordance has no durable API source — **needs a call**
Acceptance says "edit/delete on manual entries with 'edited' affordance (D3)", but D3
made the audit **invisible** and `LedgerResponse` exposes **no `edited_at`/`updated`
flag**. FE-only, the badge can only be **session-local** (§4.3). If product wants a
badge that survives reload/other-viewer, it requires a BE change (`edited_at` on the
entry or a lightweight "edited" boolean) — **out of scope for this FE WP**; recommend a
follow-up BE ticket. This spec ships the session-local badge as the minimal
acceptance-satisfying behaviour; IMPL should not fabricate a persistent flag.

### 10.2 Chores "not a primary tab" — **RESOLVED: option A implemented**
§5 wants chores de-emphasised from the primary section tabs. **IMPL took option A**
(the recommendation): the `chores` segment is dropped from `GroupSectionTabs`
(→ Overview / Loans) and the admin Overview gains an `overview-chores-link`
("Chores") entry point → `/(app)/groups/${id}/chores`. Rationale for deciding
autonomously in the autopilot run: it is exactly what §5 asks; the `/chores` route
and all its testIDs (`chores-root`/`chore-row-*`/`chores-add-button`/`chores-empty`)
are untouched, so `seeded-readonly` and `openTab(page,'chores')` (both full-URL nav)
are unaffected; and it is trivially reversible (re-add one `SECTIONS` entry) if
product prefers B. **Review flag:** this is the one visible-nav change in the WP —
revert to B by restoring the `chores` row in `GroupSectionTabs.SECTIONS` if undesired.

### 10.3 Member-initiated "new loan" from AddEntrySheet — **not required**
§3.2 keeps the 4-type picker admin-only; members still request loans on the Loans tab.
Adding "New loan" to the member sheet is **not** in §5/acceptance — left out; flag if
product wants it.

### 10.4 Loan detail write-actions — kept read-only
Loan detail (§2.3) renders schedule read-only; approve/reject/close stay on the list to
limit new surface. Flag if a "close early" affordance is wanted on the detail screen.
