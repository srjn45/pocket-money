# V3-4.4 — E2E suite v3 consolidation (SPEC)

Status: SPEC (Opus) · Owner WP: **V3-4.4** · Base: `autopilot/integration` @ `45445c7`
(Phase 1–3 + V3-4.1 nav shell + V3-4.2 statement/dashboard + V3-4.3 passbook/entry-flows/catalog all landed).

**Scope class: TEST/E2E-ONLY.** This WP rewrites/prunes the Playwright suite and its

## 0. Why this WP exists

4.1–4.3 edited the app incrementally and patched e2e selector paths along the way.
The suite now works but is organised around v2 seams: eight spec files with heavy
register/create-group boilerplate, one still exercising the **member-submission**
flow (dead under D2, default-off), and the v3 golden path scattered across three
files (`onboarding` T3 + `statement` T-STMT-* + `ledger` T5). This WP:

1. Lands a single **`golden-path.spec.ts`** that documents the v3 happy path end
   to end (§1).
2. Prunes the dead v2 flow (member-submission) and its now-orphaned helpers (§2).
3. Confirms the seed is already v3-shaped and needs no destructive backend edit (§3).
4. Hardens against the four known flake classes and defines the "zero-flaky over
   3 runs" proof (§4).

The E2E CI job (`.github/workflows/ci.yml`, job `E2E`, `needs: [build, fe-web-export]`)
is unchanged by this WP except that it runs a smaller, faster, deterministic set.
CI serves `app/dist` (built with invites **OFF** — `EXPO_PUBLIC_INVITES_ENABLED`
is unset, so `INVITES_ENABLED === false`) against a real backend seeded by
`go run ./cmd/seed --reset`. Retries are `1` in CI; the zero-flaky proof (§4.5)
runs with `--retries=0`.

### 1.3 Numeric fallback for step A.10

Primary asserts `statement-payable` = `₹320.00` (base 500 + chore 20 − EMI 200,
opening 0). This is deterministic **iff** the admin-created loan's first EMI posts
in the current period via `PostDue` on statement read. If impl finds same-month EMI
flooring makes the net figure period-sensitive (e.g. loan `start_period` rolls to
next month), fall back to: assert `statement-payable-<uid>` matches `/₹5(2|3)0\.00/`
is **not** acceptable (§9.12 forbids fuzzy) — instead **drop the loan from the
payable arithmetic**: create the loan (so the loan leg exists and is asserted via
its card/schedule per §1.4), but assert `statement-payable` = `₹520.00` (base +
chore only) and separately assert the loan card renders on the loans tab. Impl must
verify which of the two holds in CI and pick the one that is exact and stable; the
spec's requirement is a **concrete, exact** payable assertion either way.

### 1.4 New API helper `apiCreateLoan` (in `e2e/support/api.ts`)

Admin creates a pre-approved active loan for a member (openapi `createLoan`,
"admin creates a pre-approved `active` loan for a member"; `user_id` required for
the admin path). Signature:

```ts
export async function apiCreateLoan(
  token: string, groupId: string, userId: string,
  principalMinor: number, installments: number, currency: Currency = 'INR',
): Promise<{ id: string }> {
  return request(`/groups/${groupId}/loans`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${token}` },
    body: JSON.stringify({ user_id: userId, principal: { currency, value: principalMinor }, installments }),
  });
}
```

This keeps the loan leg of the golden path within the shadow-member journey without
requiring the member to claim first (shadow users cannot authenticate, §3.1, so a
member-*requested* loan is impossible pre-claim). The live **member-requested** loan
path is retained in `loans.spec.ts` / `loan-detail.spec.ts` (§2).

## 4. Flake-hardening (the "zero flaky over 3 runs" proof)

The four known flake classes (project memory + master-plan §9.12) and how the
consolidated suite neutralises each:

### 4.1 AuthGate invite/claim race
`AuthGate` is the single post-auth navigator; a claim (register with a shadow email)
must land on `dashboard-root` before any group navigation. Every claim path uses
`addMemberAndClaim` / the golden-path step 13→14 sequence: **await `dashboard-root`
first, then `page.goto('/groups/<id>')`** — never chain group nav off the register
submit. No per-screen post-auth navigation is added.

### 4.2 expo-router web param discipline
Group-scoped screens read `[id]` from `useLocalSearchParams`; a tab-link click does
**not** populate `[id]` on web. All group-tab navigation goes by **full URL**
(`openTab` uses `page.goto(\`/groups/${gid}/${suffix}\`)`; profile — no dynamic
segment — uses the tab link). Golden-path re-entry to the overview after the member
detour uses `page.goto(\`/groups/${gid}\`)`, not a back-nav.

### 4.3 native-Stack hidden-screen duplication
The flattened nav (V3-4.1) is a native Stack: a pushed screen keeps the previous
screen mounted (`display:none`, `aria-hidden`) in DOM order **before** the active
one, so an unscoped `.first()` can resolve the stale hidden copy. Mitigation, applied
at every drill-in assertion: **scope `getByText`/`getByTestId` to the active screen's
root testID** before `.first()`. Concretely golden-path step A.7 uses
`page.getByTestId('member-detail-root').getByText(/₹500\.00/).first()` (the exact
guard the old `ledger` T5 documented). Where a bare root testID is asserted
(`member-detail-root`, `loan-detail-root`) Playwright's visibility check already
ignores the `display:none` copy.

### 4.4 PostDue timing — assert counts/final state, not fixed transient states
`PostDue` runs on statement/dashboard read; posted-row counts and periods can drift
with wall-clock month boundaries. The suite asserts **authoritative final figures**
(`statement-payable`/`statement-remaining` exact text after invalidation) and
**counts** (`member-card-*` `toHaveCount(1)`; loan installment count = installments),
never a fixed count of transient PostDue rows. Success is always a **state change**
(sheet closes, badge appears, figure recomputes), never absence-of-failure (§9.12).
The golden-path payable assertion is pinned to exact, engine-derived arithmetic
(§1.3) with an explicit fallback so it stays exact if same-month EMI flooring shifts.

### 4.5 The proof
"Zero flaky over 3 consecutive runs" is demonstrated by the impl/review stage running
the E2E job **three times back-to-back with retries disabled**:

```
cd e2e && for i in 1 2 3; do npx playwright test --retries=0 --workers=2 || exit 1; done
```

(mirrors CI `workers: 2`, but `--retries=0` so a real flake cannot be masked by the
CI `retries: 1`). All three passes green ⇒ criterion met. CI itself keeps
`retries: 1` as production insurance; the 3× `--retries=0` loop is the acceptance gate.
Because integration/e2e run **only in CI** (no Docker locally — §9.3), this loop is
run against the CI environment / the PR's E2E job, not the dev host.

### Two discoveries flagged for the brain (NOT fixed here — out of e2e scope)

1. **D2 UI gap (product):** `member-log-chore` ("Log a chore") in
   `app/app/(app)/groups/[id]/index.tsx:~373` is rendered **unconditionally** — it is
   **not** gated on the group's `member_chore_submission_enabled` flag. Per D2 the
   member-submission UI should be "inert when off" (default off), yet the button is
   always visible and the API returns 403 on submit. This is a **product-code (app/)
   defect**, not a testID contract break, so this WP does not touch it and does not
   add an assertion that would fail against current source. Recommend a follow-up
   (V3-4.x FE) to gate the button on `member_chore_submission_enabled`. Pruning T4
   is still correct: the flow is dead by default and not part of the v3 golden path.

2. **No testID contract break found.** Every selector the kept/new suite needs exists
   at `45445c7`; the consolidation preserves all of them. No product-code exception
   under the "fix a genuinely broken testID contract" carve-out is needed.
