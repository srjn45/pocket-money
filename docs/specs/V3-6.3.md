### 1.3 Why the bell lives in a separate spec (anti-redundancy guard — do NOT "fix")

`golden-path.spec.ts` Test A adds the member as a **shadow** (add-by-email of an
unregistered address). Per §3.7 / V3-5.2, the **N-1 "added to group"
notification fires only for a *registered* user** — a shadow add writes no
notification. So the bell cannot be asserted inside Test A without changing the
add-by-email-then-claim ordering that the test exists to prove.
`notifications.spec.ts` correctly covers the bell by registering the member
**first**, then adding them. This split is **intentional and correct**. A
reviewer/implementer must **NOT** manufacture a redundant bell assertion inside
`golden-path.spec.ts` — the compose-smoke run executes *both* files against the
single image, so the composite golden path (spine + bell) is proven by the job
as a whole.

### 1.4 Why the opening/closing invariant stays a BE-integration assertion

The `closing(M) == opening(M+1)` invariant is a statement-**math** property,
asserted deterministically in the BE integration tests (V3-3.1, `Test` job,
`-tags=integration`) across a backfilled 3-month ledger. e2e proves the
statement **screen renders the correct figure** (₹520.00 / ₹0.00). Do **not**
add an e2e assertion for the invariant — it would be a weaker, flakier
restatement of an already-green backend guarantee. §9.3: integration tests are
the gate for backend math; e2e is the gate for the UI wiring.

### 1.5 Two-currency requirement is satisfied without duplicating the spine

§8 requires "INR + EUR groups"; §11 requires the golden path "in two
currencies". The full spine (claim / payment / loan) is proven **once** in INR
(Test A); EUR coverage proves **currency propagation** end-to-end (dashboard +
posted chore, Test B). Because currency is a per-group property that flows from
the group everywhere (D7), re-running the entire spine in EUR would be redundant.
Do **NOT** add a full EUR spine.

### 1.6 Compose-smoke wiring (VERIFY this is what proves DONE)

`.github/workflows/ci.yml` job **`compose-smoke`** (name: *"Compose Smoke
(single-image e2e)"*, added in V3-6.1):

- `docker compose up -d --build` → builds the **root multi-stage `Dockerfile`**
  (web export → go build → alpine) and boots `postgres` + `app` (the single image).
- waits on `http://localhost:8080/health`; seeds via host `go run ./cmd/seed`.
- runs `npx playwright test` with `E2E_WEB_BASE=http://localhost:8080`,
  `E2E_API_BASE=http://localhost:8080/api/v1`, `E2E_EXTERNAL_SERVER=1`
  → Playwright uses the **single origin** (no `npx serve`; `webServer` disabled
  in the config when `E2E_EXTERNAL_SERVER` is set) and thus exercises the
  **packaged artifact, same-origin API at `/api/v1`**, not the dev servers.

Because `npx playwright test` runs the whole `testDir`, **`golden-path.spec.ts`
and `notifications.spec.ts` both run against the single image.** This IS the DoD
gate ("golden path covered by e2e AND executed against the V3-6.1 image").
