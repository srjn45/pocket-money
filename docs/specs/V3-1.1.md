# V3-1.1 — Backend currency (D7)

**Phase 1 · Backend half of the currency work.** Binding contract:
`docs/master-plan-v3.md` §2 (D7), §3.2, §3.8, §8 (V3-1.1 row), §9. Storage stays
`int64` minor units — this WP changes the **API money shape and the group
currency**, never the money arithmetic.

Ships in **one combined PR with V3-1.2** (see `docs/notes/phase1-combined-pr.md`):
V3-1.1 is a breaking runtime change to every amount field, so e2e stays red until
the FE matches. Do not open a BE-only PR.

## 0. Codegen mechanism (state it, don't guess)

- **Backend Go types are HAND-WRITTEN.** There is no `oapi-codegen` in `go.mod`;
  `openapi.yaml` is the *contract document*. Request/response structs are
  maintained by hand in `backend/internal/models/models.go` and in each handler
  file (`handlers/*.go`). **You must edit `openapi.yaml` AND the matching Go
  structs by hand, and keep them identical** (§9.1 contract-first: edit
  `openapi.yaml` first, then mirror in Go).
- **Frontend types ARE generated** from `openapi.yaml` via
  `openapi-typescript` (`npm run codegen` → `app/src/api-types.gen.ts`). That is
  V3-1.2's job; your only obligation here is that `openapi.yaml` is correct and
  valid, because the FE regenerates from it.

## 1. Migration — `groups.currency`

New paired migration, next sequential number **013** (012 is the last existing):

- `backend/migrations/013_group_currency.up.sql`
- `backend/migrations/013_group_currency.down.sql`

Mechanism is `golang-migrate` with a `file://` source (see `db/migrate.go`) —
plain SQL files, no `iofs` embed (that arrives in Phase 6). Re-runnable on a
fresh DB and idempotent-safe (§9.4).

**up:**

```sql
-- 013_group_currency.up.sql
-- D7: every group has an immutable currency in {EUR, USD, INR}.
-- Add with a temporary DEFAULT so existing rows backfill to INR in one shot,
-- then drop the default so future inserts MUST supply a currency explicitly.
ALTER TABLE groups
    ADD COLUMN IF NOT EXISTS currency char(3) NOT NULL DEFAULT 'INR';

ALTER TABLE groups
    ADD CONSTRAINT groups_currency_check CHECK (currency IN ('EUR', 'USD', 'INR'));

ALTER TABLE groups
    ALTER COLUMN currency DROP DEFAULT;
```

**down:**

```sql
-- 013_group_currency.down.sql
ALTER TABLE groups DROP CONSTRAINT IF EXISTS groups_currency_check;
ALTER TABLE groups DROP COLUMN IF EXISTS currency;
```

Notes:
- `char(3)` matches §3.2 exactly. All three codes are exactly 3 chars, so there
  is **no space-padding hazard** — `'EUR'`/`'USD'`/`'INR'` scan back clean.
- Existing rows → `'INR'` (D7). Verified by the backfill default.
- Keep `TestMigrations_Idempotent` green (known flake — re-run once per §11 before
  treating a failure as real).

## 2. `openapi.yaml` — the `Money` schema

Add one schema under `components.schemas`:

```yaml
Money:
  type: object
  description: >
    A monetary amount in a group's currency. `value` is in minor units
    (cents/paise; all three supported currencies have exponent 2) and is NEVER a
    float. `currency` always equals the owning group's currency (D7); the server
    rejects any request whose currency differs from the group's.
  properties:
    currency:
      type: string
      enum: [EUR, USD, INR]
      description: ISO-4217 code; always the owning group's currency.
    value:
      type: integer
      format: int64
      description: Amount in minor units (e.g. €12.50 = 1250). Always an integer.
  required:
    - currency
    - value
```

**Design decision — ONE schema for both directions.** `Money` is reused for
request and response fields; both members are `required`. D7 says a request "may
omit / must-match" the currency, but a single required-both schema is cleaner for
hand-written Go + codegen and imposes no burden: the FE always holds the group's
currency (from group detail) and sends it. The server still enforces match (§4).
`minimum` on `value` is expressed per-field where the old field had it (chores
`>=1`, allowance `>=0`) via a `description` note, **not** inside `Money` (a shared
schema can't carry per-field minimums) — the handler enforces the bound (§4).

### Go mirror

Add to `models/models.go`:

```go
// Money is the API representation of a monetary amount (D7). Storage stays int64
// minor units; this is purely the (de)serialization shape.
type Money struct {
    Currency string `json:"currency"`
    Value    int64  `json:"value"`
}

func NewMoney(currency string, value int64) Money {
    return Money{Currency: currency, Value: value}
}
```

Supported-currency constants + a validator also live in `models` (reused by
group-create validation and mismatch checks):

```go
const (
    CurrencyEUR = "EUR"
    CurrencyUSD = "USD"
    CurrencyINR = "INR"
)

func IsValidCurrency(c string) bool // true for EUR/USD/INR
```

### 3c. Request amount fields → `Money`

| # | openapi schema.field · Go struct.field | Old bound (enforce in handler) |
|---|---|---|
| Q1 | `CreateChoreRequest.amount` · `chores.CreateChoreRequest.Amount` | `value >= 1` |
| Q2 | `UpdateChoreRequest.amount` · `chores.UpdateChoreRequest.Amount` (nullable) | `value >= 1` when present |
| Q3 | `CreateLedgerRequest.amount` · `ledger.CreateLedgerRequest.Amount` (nullable) | `value >= 1` when present (settlement/adjustment) |
| Q4 | `SetAllowanceRequest.amount` · `allowances.SetAllowanceRequest.Amount` | `value >= 0` (0 = paused) |
| Q5 | `CreateLoanRequest.principal` · `loans.CreateLoanRequest.Principal` | `value >= 1` |
| Q6 | `ApproveLoanRequest.principal` · `loans.ApproveLoanRequest.Principal` (nullable) | `value >= 1` when present |

`gin` binding tags (`binding:"required,gt=0"`) that lived on the old scalar move
to explicit handler checks, because `gt=0` can't be expressed on a nested struct

(§4), (b) numeric bound above, else `400`.

`LoanResponse.installments_posted`, `GroupSummaryResponse.member_count`,
`GroupDetailResponse.chores_count`, `InviteRequest.expires_in_days`.

## 4. Handler changes

### 4a. Group create takes required currency

`handlers.CreateGroupRequest` → add `Currency string \`json:"currency" binding:"required"\``.
In `CreateGroup` (`handlers/groups.go`): after bind, `if !models.IsValidCurrency(req.Currency)` → `400 {"error":"currency must be one of EUR, USD, INR"}`.
`GroupRepo.Create` signature becomes
`Create(ctx, name string, headUserID uuid.UUID, currency string)`; INSERT adds
the `currency` column. Response (`GroupResponse`) includes `group.Currency`.

`GroupRepo.GetByID` and `GroupRepo.ListForUserWithSummary` **must select
`currency`** (`g.currency`) and populate `models.Group.Currency` /
`GroupSummary.Currency`. Every place that reads a group now has its currency for
free — use it to build `Money`.

### 4b. Serialize group currency into every Money (responses)

Each response builder wraps its int64 in `models.NewMoney(groupCurrency, value)`.
Handlers that don't already load the group must fetch its currency:
- `chores.go` list/create/update: the chore's group is in the path (`:id`) for
  list/create; for `PATCH/DELETE /chores/{id}` load the chore, then its group's
  currency (add a lightweight `GroupRepo.GetCurrency(ctx, groupID)` helper, or
  reuse `GetByID`).
- `ledger.go`, `loans.go`, `allowances.go`: group id is in the path — one
  `GetCurrency` call per request, pass down to the response builder.

Add `GroupRepo.GetCurrency(ctx, groupID) (string, error)` (single-column select)
to avoid loading the whole group where only the code is needed.

### 4c. Reject currency mismatch on writes (400, human-readable)

For every request carrying a `Money` (Q1–Q6), after binding:

```go
if body.Amount.Currency != groupCurrency {
    c.JSON(http.StatusBadRequest, gin.H{
        "error": fmt.Sprintf("amount currency %s does not match group currency %s",
            body.Amount.Currency, groupCurrency),
    })
    return
}
```

Then apply the numeric bound (§3c). Downstream repo/posting code keeps receiving
a plain `int64` (`body.Amount.Value`) — **money math is untouched** (D7/§3.8).
For chore-type ledger entries the amount comes from chore config and the request
amount is ignored today; keep that — but if a `Money` is supplied, still
validate its currency (reject mismatch) for consistency.

### 4d. Money math stays int64

No changes to `posting/`, `::bigint` casts, `ledger_repo` balance SQL, loan EMI
`ceilDiv`, or any arithmetic. `Money` exists only at the JSON boundary. This is
the single most important invariant of this WP (§3.8: "Storage is unchanged").

## 6. Test plan (integration — CI only, §9.3)

New/updated tests in `handlers/*_integration_test.go` (run under the
`integration` build tag; no local Docker — CI is the gate):

1. **Create group per currency** — POST `/groups` with each of `EUR/USD/INR`
   succeeds (201) and the response `currency` echoes the request.
2. **Group create rejects bad/missing currency** — missing → 400; `"GBP"` → 400;
   lowercase `"eur"` → 400 (enum is exact-case).
3. **Mismatched-currency write rejected** — in an INR group, POST a chore /
   ledger adjustment / allowance / loan whose `amount.currency = "EUR"` → 400 with
   the human-readable message; matching currency → success.
4. **Every Money response carries the group currency** — chore, ledger entry,
   balance, allowance, loan, group-summary responses all serialize
   `{currency: <group>, value: <int64>}`; assert both fields.
5. **Isolation** — an INR group and a EUR group; each group's responses report
   its own currency; no endpoint sums across them.
6. **All existing money-math tests pass unchanged** — balance, posting, loan EMI,
   allowance backfill suites are storage-level and must not need edits beyond
   updating any assertion that reads a now-`Money` JSON field. Update those
   assertions to read `.amount.value` etc.; the numeric expectations do not change.

Local gates before pushing (§9.3): `make -C backend test lint`, `go vet` both
build tags, `gofmt`. Integration + e2e are CI-only.
