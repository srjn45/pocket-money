## 0. Scope summary & decisions

This WP delivers four things plus their OpenAPI surface:

1. **Edit / delete of manual ledger entries** (`chore_credit`, `adjustment`,
   `clearing`) — `PUT`/`DELETE /api/v1/ledger/{id}`. System entries
   (`base_credit`=`allowance`, `EMI debit`=`emi`) → **403**. Admin-only (D6).
2. **`entry_audit`** table (migration 016) — invisible prior-value snapshot,
   written on **every** edit and delete, before the mutation.
3. **`groups.member_chore_submission_enabled`** flag (migration 016, `bool NOT NULL
   DEFAULT false`, D2) gating the member chore-submission workflow, plus a
   `PATCH /api/v1/groups/{id}` admin toggle and the flag in group responses.
4. **`chores.description`** — **already present** (see §6 scope flag); the only
   actionable gap is wiring the already-written `PATCH /api/v1/chores/{id}` route.

### Type ⇄ API-name map (from V3-3.1 / §3 entry-type table)

| Plan name (§3) | API/DB `entry_type` | Sign / direction | Origin | Editable (D3) |
|---|---|---|---|---|
| base_credit | `allowance` | + credit | system (`PostDue`) | **no → 403** |
| chore_credit | `chore` | + credit | admin picks member+chore | **yes** |
| adjustment | `adjustment` | ± | admin one-off | **yes** |
| EMI debit | `emi` | − debit | system (`PostDue` from loan) | **no → 403** |
| clearing / payment (D9) | `settlement` | − debit | admin records payment | **yes** |

Manual = `{chore, adjustment, settlement}`. System = `{allowance, emi}`.

### Decisions taken within D1–D9 latitude (none require operator escalation)

- **Edit/delete auth = admin-only.** §4 permissions matrix row *"Add/edit/delete
  manual ledger entries — Admin ✅ / Member ❌"* is explicit. Members → **403**.
- **Flag-gate status code = 403** (chosen over 404). The group and route exist and
  the caller is an authenticated member; the action is forbidden by group config.
  403 with a clear message is truthful and avoids implying the path is conditionally
  absent. The §8 acceptance row permits "404/403"; 403 is used consistently for all
  three gated points.
- **Delete = hard delete** of the `ledger_entries` row (not soft-delete). This keeps
  the statement/balance/summary queries unchanged (they already read only surviving
  `status='approved'` rows), so the invariant stays structural with zero query
  churn. `entry_audit` preserves the full prior row, so nothing is lost. See §2 for
  the `ON DELETE SET NULL` FK that lets the parent delete proceed while the audit row
  survives.
- **Edit is a full replace of the mutable fields** (`amount`, `note`, and
  `direction` for adjustments only). `entry_type`, `user_id`, `chore_id`,
  `created_at`, `period`, `status`, `loan_id`, and decided_* are **immutable** — this
  is what keeps an edited entry in the same `effMonth` bucket (invariant-safe, §5).
- **A chore edit may set a custom amount.** On *create*, a chore entry's amount is
  taken from the chore config and any custom amount is ignored. On *edit* (a D3
  correction) the admin-supplied amount is applied directly — that is the entire
  point of "edit a chore amount → statement updates" (V3-4.3). Intentional asymmetry,
  justified by D3.

No money/auth semantics here fall outside D1–D9, so there is nothing to escalate.

## 1. Edit / delete contract

### 1.1 Routes (register in `cmd/server/main.go`, protected group)

```
PUT    /api/v1/ledger/:id     ledgerHandler.EditLedger      (admin-only, manual types)
DELETE /api/v1/ledger/:id     ledgerHandler.DeleteLedger    (admin-only, manual types)
```

Same `:id` path family as the existing `POST /api/v1/ledger/:id/approve|reject`.

### 1.2 Editable fields by type

| `entry_type` | `amount` | `direction` | `note` | notes |
|---|---|---|---|---|
| `chore` | editable, `value>=1` | fixed `credit` — **must be absent** (400 if sent) | editable | chore_id NOT editable |
| `adjustment` | editable, `value>=1` | **required**, `credit`\|`debit` | editable | |
| `settlement` | editable, `value>=1` | fixed `debit` — **must be absent** (400 if sent) | editable | |
| `allowance`, `emi` | — | — | — | **403** — not directly editable |

- `amount` is a `Money{currency,value}`. `value` is minor units, `>= 1`. `currency`
  **must equal the group's** (`checkMoneyCurrency`, reused from create); mismatch →
  **400**. Currency is never changed by an edit (immutable per group, D7).
- `note` is full-replace: the provided value replaces the stored note; **omitted or
  `null` → note set to `NULL`** (PUT = replace-the-editable-fields semantics; the
  correction UI resends the current note). Description edits on a *chore entry* mean
  editing this `note` field — the ledger entry has no separate description; the
  chore-catalog `description` is a property of the chore, edited via
  `PATCH /chores/{id}` (§6).

### 1.3 Request body — `EditLedgerRequest`

```jsonc
{
  "amount":    { "currency": "INR", "value": 1500 },  // required, value>=1, currency==group
  "direction": "debit",                                // adjustment ONLY (required there); 400 if sent for chore/settlement
  "note":      "corrected amount"                      // optional; null/absent clears the note
}
```

### 1.4 Handler flow (both `EditLedger` and `DeleteLedger`)

1. Auth → user id (401 if absent).
2. Parse `:id` (400 if not a UUID).
3. `ledgerRepo.GetByID(id)` → **404** if `ErrNotFound`.
4. `groupRepo.GetMember(entry.GroupID, userID)` → **403** "not a member of this
   group" if `ErrNotFound`.
5. `member.Role != RoleAdmin` → **403** "only group admin can edit/delete entries"
   (D6).
6. `entry.EntryType ∈ {allowance, emi}` → **403** `"system-generated entries cannot
   be edited or deleted; edit the base amount or loan instead"`. (Status-agnostic:
   applies to manual entries in any status; the D2 flag does NOT gate corrections —
   it gates *submission* only.)
7. **Edit only:** bind `EditLedgerRequest`; `checkMoneyCurrency(amount, currency)`;
   `amount.Value < 1` → 400; direction rule per §1.2 table.
8. **Transaction** (`pool.Begin` → `defer Rollback` → `Commit`), all on the tx
   `Querier`:
   a. `GetForUpdate(tx, id)` — re-read the row `FOR UPDATE` (lock; also the
      snapshot source). If gone → 404 (lost race).
   b. `auditRepo.Insert(tx, entryID=id, oldRow=json.Marshal(preEntry),
      action, actor=userID)` — **prior values, before mutation**.
   c. Edit: `ledgerRepo.UpdateManualEntry(tx, id, amount, direction?, note)` →
      returns updated row. Delete: `ledgerRepo.DeleteEntry(tx, id)`.
   d. Commit.
9. Edit → **200** `LedgerResponse` (updated, currency-wrapped via
   `entryToResponse`). Delete → **204** no content.

### 1.5 Auth / scoping citation

D6 (§4 permissions matrix): *"Add/edit/delete manual ledger entries — Admin ✅,
Member ❌, Shadow —"*. Enforced in the backend (step 5), mirrored — not relied on —
in the UI (Phase 4). This reuses the existing admin gate pattern from
`CreateLedger`/`ApproveLedger`.

## 2. `entry_audit` (migration 016)

Invisible (no read API in this WP). One row per edit/delete, capturing the **full
pre-change ledger row** as `jsonb`.

### 2.1 DDL — `migrations/016_corrections_and_flags.up.sql`

```sql
-- V3-3.2: (1) entry_audit — invisible prior-value log for manual-entry
-- edits/deletes (D3, §3.5). (2) groups.member_chore_submission_enabled — the D2
-- gate for the member chore-submission workflow, default OFF.
-- NOTE: chores.description is NOT added here — it already exists (migration 003).

-- (1) entry_audit. old_row is the JSON snapshot of the ledger_entries row taken
-- BEFORE the edit/delete. entry_id uses ON DELETE SET NULL so a hard delete of the
-- parent entry succeeds while the audit row (and its old_row snapshot, which holds
-- the original id) survives. No read API in MVP.
CREATE TABLE IF NOT EXISTS entry_audit (
    id       uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    entry_id uuid        NULL REFERENCES ledger_entries(id) ON DELETE SET NULL,
    old_row  jsonb       NOT NULL,
    action   text        NOT NULL CHECK (action IN ('edit', 'delete')),
    actor    uuid        NOT NULL REFERENCES users(id),
    at       timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_entry_audit_entry ON entry_audit (entry_id);

-- (2) D2 flag. Default OFF so existing groups keep today's admin-only ledger
-- behavior; a member can submit chores only when an admin turns this on.
ALTER TABLE groups
    ADD COLUMN IF NOT EXISTS member_chore_submission_enabled boolean NOT NULL DEFAULT false;
```

### 2.2 Down — `migrations/016_corrections_and_flags.down.sql`

```sql
DROP INDEX IF EXISTS idx_entry_audit_entry;
DROP TABLE IF EXISTS entry_audit;
ALTER TABLE groups DROP COLUMN IF EXISTS member_chore_submission_enabled;
```

Paired up/down, sequential (016), re-runnable on a fresh DB (§9.4);
`TestMigrations_UpAndDown` rolls the whole chain, so the down must be clean.

### 2.3 `old_row` snapshot

`old_row` = `json.Marshal(preEntry)` where `preEntry` is the `*models.LedgerEntry`
read `FOR UPDATE` in the same tx. Keys follow the model's json tags
(`amount`, `entry_type`, `user_id`, `direction`, `status`, `note`, `created_at`,
…), so a test can assert `old_row->>'amount'` and `old_row->>'entry_type'` against
the original. (Equivalently `row_to_json(le)` in SQL — either is acceptable; marshal
is used for one code path and easy assertions.)

### 2.4 Insert query (sqlc-style, in `db/audit_repo.go`)

```sql
-- InsertEntryAudit :exec
INSERT INTO entry_audit (id, entry_id, old_row, action, actor)
VALUES (gen_random_uuid(), $1, $2, $3, $4);
```

```go
func (r *AuditRepo) Insert(ctx context.Context, q Querier,
    entryID uuid.UUID, oldRow []byte, action string, actor uuid.UUID) error
```

Repo runs on a `Querier` (pool or tx) so it participates in the edit/delete tx.
`action` values: `models.AuditActionEdit = "edit"`, `models.AuditActionDelete =
"delete"`.

## 3. `member_chore_submission_enabled` flag (D2)

Default **false**. When OFF the member chore-submission workflow is inert; when ON it
behaves as today.

### 3.1 Exact endpoints gated (all pre-existing)

There is **no dedicated `/submit` route** in this codebase — member chore submission
is `POST /groups/{id}/ledger` with `entry_type=chore` from a non-admin (it creates a
`pending_approval` entry). The full workflow is three endpoints:

| Endpoint | Handler | Gate when flag OFF |
|---|---|---|
| `POST /api/v1/groups/{id}/ledger` (non-admin, `entry_type=chore`) | `CreateLedger` | **403** `"member chore submission is disabled for this group"` — *before* creating the pending entry |
| `POST /api/v1/ledger/{id}/approve` | `ApproveLedger` | **403** same message |
| `POST /api/v1/ledger/{id}/reject`  | `RejectLedger`  | **403** same message |

- The gate applies **only to the member-submit branch** of `CreateLedger`
  (`!isAdmin && entry_type==chore`). Admin-created chore entries (auto-approved),
  settlements, and adjustments are unaffected by the flag.
- `ApproveLedger`/`RejectLedger` read the flag via the fetched `entry.GroupID`,
  after the existing membership + admin checks, and return 403 when OFF.
- **Operational caveat (document in code):** disabling the flag while
  `pending_approval` entries exist leaves them pending (excluded from the statement —
  it reads `approved` only); it does not auto-reject them. In practice pending
  entries can only exist while the flag was ON. Out of scope to auto-resolve them.

When ON: member submit → **201** `pending_approval` (unchanged); approve → **200**
approved; reject → **200** rejected (all as today).

### 3.2 Admin toggle — `PATCH /api/v1/groups/{id}`

Needed so an admin can turn the flag ON (and so the "functional when on" acceptance
is reachable via the API, not just DB). Admin-only.

- Body `UpdateGroupRequest`: `{ "member_chore_submission_enabled": true }` (the only
  editable group field in this WP — name/currency stay immutable here).
- Flow: auth → parse id → `GetMember` (403 if not member) → `role!=admin` → 403 →
  bind → `groupRepo.SetChoreSubmissionEnabled(id, enabled)` → **200**
  `GroupResponse` (now including the flag).
- Register: `protected.PATCH("/groups/:id", groupHandler.UpdateGroup)`.

### 3.3 Flag surfaced in responses

Add `member_chore_submission_enabled bool` to `GroupResponse` (returned by
`CreateGroup`, `UpdateGroup`) and `GroupDetailResponse` (returned by `GetGroup`).
`GroupRepo.GetByID` SELECT and scan add the column; `models.Group` gains the field.
(Dashboard `GroupSummary`/`ListForUserWithSummary` does **not** need it — leave
unchanged.)

## 5. Statement interplay (invariant preservation)

`statement.Compute` (V3-3.1) is **unchanged**. It reads a member's `status='approved'`
entries, buckets each by `effMonth` (system entries by `Period`; manual entries by
`FormatPeriodLocal(created_at)`), accumulates `signed()` into opening (`< M`) and the
month figures (`== M`), and derives `total_due` / `closing`. The invariant
`closing(M) == opening(M+1)` holds because both are the same running
`Σ signed(e) over effMonth ≤ M`.

**Why edit/delete preserve it:**

- An **edit** only mutates `amount` (and, for adjustments, `direction`) and `note`.
  It never touches `created_at`, `period`, `entry_type`, `user_id`, or `status`, so
  the entry stays in the **same `effMonth`** and the **same member**. Changing the
  magnitude by Δ changes `closing(M)` by `±Δ` and `opening(M+1)` by the **same**
  `±Δ` (both are the same signed sum), so `closing(M) == opening(M+1)` after the
  correction. Editing an adjustment's direction flips its `signed()` contribution,
  which likewise moves both sides equally.
- A **delete** hard-removes one approved row; every later month's opening and that
  month's closing drop by exactly `signed(deleted)` — again equal on both sides. All
  other statement/balance/summary queries read only surviving `approved` rows, so
  they recompute correctly on the next `GET /statement` (which triggers `PostDue`
  then re-reads the ledger).
- Manual entries always have `period = NULL`, so `effMonth = month(created_at)`;
  since `created_at` is immutable across an edit, no entry can migrate between months
  — no cross-month leakage.

**Invariant test (names — see §7):**
`TestCorrections_EditRecomputesAndPreservesInvariant` (integration) proves it
end-to-end across a month boundary; `TestCompute_EditedAmountPreservesInvariant`
(pure unit, statement pkg) proves the Compute-level property with no DB.

- **Edit-recompute + invariant**: seed an approved `chore` entry in month M
  (`backdateEntry` to mid-M), give the member an allowance backfilled to ≤ M so M and
  M+1 both have rows; `GET /statement?period=M` and `?period=M+1`, record

- **System-entry reject**: trigger `PostDue` (via `GET /statement` or `/balance`) to
