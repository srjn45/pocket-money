## 0. Summary & the two halves of this WP

This WP does two things:

1. **Rename `head` → `admin`, end-to-end and reversibly** — the per-membership
   role value, the group-owner column `groups.head_user_id`, and every mirror of
   those in openapi + hand-written Go + repos + posting + seed + integration
   tests. Acceptance requires **zero `head` remaining in `openapi.yaml`**.
2. **Enforce D6 member scoping in the backend** — an **admin** of a group sees
   every member's money data; a plain **member** may read **only their own**
   ledger / balance / loans / base-amount rows, enforced from the auth-context
   user id + membership role, never from a client-supplied scope.

**Behavioral security surface is small and precise.** Ledger, loans and
allowances **already** scope members to their own rows; the one real D6 **hole**
is `GET /groups/:id/balance`, which today returns **every** member's balance to
**any** member. Everything else in the scoping section is (a) closing that hole,
(b) making a member's explicit cross-member request an **explicit 403** instead
of a silent narrow, and (c) the mechanical rename. See §3.

### 0.1 Scope decision — the FE/e2e rename rides with this BE WP (justified)

The plan splits BE rename (V3-2.2) from FE rename (V3-2.3). **But CI runs the
full Playwright e2e job on every PR into `autopilot/integration`** (`.github/
workflows/ci.yml`, `on: pull_request: branches: [… autopilot/integration]`), and
e2e serves the **committed** Expo web bundle against the **renamed** backend.
§11's gate is "merge only on full CI green **including the E2E job**." If V3-2.2
renames the API to return `role:"admin"` / `admin_user_id` but the shipped app
still compares `role === 'head'`, the dashboard's `groups.filter(g => g.role ===
'head')` returns empty and `seeded-readonly.spec.ts` T-RO-1 fails → red PR.

Therefore V3-2.2 **must** include the **minimal, mechanical, structural** FE
rename needed to keep e2e green: regenerate the API client and flip the
`role === 'head'` / `!== 'head'` comparisons to `'admin'`. This is
correctness-driven, not feature work. **V3-2.3 is thereby reduced** to: the new
add-member-by-email sheet, shadow badge, invite-flag UI, and the *user-visible
copy* sweep ("Head" → "Admin" in display strings) — none of which V3-2.2
touches. See §5 (FE) for the exact, bounded file list. **Handoff/pipeline note:
V3-2.3 must rebase on V3-2.2** (they overlap in `app/`, so they are serial, not
∥ — consistent with §11's "openapi/shared FE files ⇒ serial").

## 1. Migration 015 — `head`→`admin` rename (paired, reversible, no data loss)

Next sequential number is **015** (014 is the last existing migration). Files:

- `backend/migrations/015_rename_head_to_admin.up.sql`
- `backend/migrations/015_rename_head_to_admin.down.sql`

### 1.1 Decision: rename the enum value AND the column (both), justified

- **Role value** is a Postgres **enum** `member_role AS ENUM ('head','member')`
  (migration 002). Use **`ALTER TYPE member_role RENAME VALUE 'head' TO 'admin'`**
  rather than a CHECK/text rebuild. RENAME VALUE is transactional and rewrites
  **every existing `group_members.role` row in place** (rows reference the label
  by oid), so pre-existing `'head'` memberships become `'admin'` **atomically —
  no `UPDATE`, no enum rebuild**. The type ends as exactly `('admin','member')`,
  satisfying "update/replace the enum to ('admin','member')". Trivially
  reversible.
- **Column**: rename **`groups.head_user_id` → `groups.admin_user_id`** (and its
  index). **Justification (explicit, as §1 of the charter requires):** the
  acceptance criterion is "openapi has **no `head`** remaining"; `head_user_id`
  is the last structural `head` token on the API surface, and this repo's
  convention is column ⇄ Go model ⇄ openapi field names kept identical (§9.6
  spirit). Leaving the column as `head_user_id` while the role is `admin` creates
  permanent naming drift. The rename is a pure `RENAME COLUMN` — **zero data
  loss**, fully reversed in `down`.

### 1.2 Re-runnability / the known flake

golang-migrate is **version-tracked**: `RunMigrations` calls `m.Up()`, which
applies 015 **exactly once**; a second `Up()` returns `ErrNoChange` without
re-executing 015's body. `TestMigrations_Idempotent` does `Up → Up(noop) →
Down` — so 015's SQL is never physically re-executed, and "re-runnable" is
satisfied by version tracking **plus** a `down` that restores the *exact* pre-015
schema. Bare `RENAME` statements are therefore correct and safe (no fragile
`DO`-block guard around `ALTER TYPE … RENAME VALUE`, which has transaction-context
caveats). `idx` rename uses `IF EXISTS` for good measure.
`TestMigrations_Idempotent` is a **known CI test-isolation flake** — re-run once
before treating a first-hit failure as real.

### 1.3 Exact SQL

`015_rename_head_to_admin.up.sql`:

```sql
-- V3-2.2: rename per-membership role 'head'->'admin' and group owner column
-- groups.head_user_id -> groups.admin_user_id (§3.2/§4/§6 Naming). D6 authz
-- scoping is code-only; this migration is the naming half. Reversible, no data
-- loss. golang-migrate applies 015 exactly once (version-tracked).

-- 1. Rename the enum label in place. Transactional; rewrites every existing
--    group_members.role='head' row to 'admin' atomically (no UPDATE needed).
ALTER TYPE member_role RENAME VALUE 'head' TO 'admin';

-- 2. Rename the group-owner column + its index to match the role vocabulary.
ALTER TABLE groups RENAME COLUMN head_user_id TO admin_user_id;
ALTER INDEX IF EXISTS idx_groups_head_user_id RENAME TO idx_groups_admin_user_id;
```

`015_rename_head_to_admin.down.sql`:

```sql
-- Reverse V3-2.2 renames; restores the exact pre-015 schema, zero data loss.
ALTER INDEX IF EXISTS idx_groups_admin_user_id RENAME TO idx_groups_head_user_id;
ALTER TABLE groups RENAME COLUMN admin_user_id TO head_user_id;
ALTER TYPE member_role RENAME VALUE 'admin' TO 'head';
```

**Do not touch prior migrations.** On a fresh DB, 012 (`INSERT … SELECT
g.head_user_id …`) runs *before* 015, when the column is still `head_user_id`, so
it stays valid. 015's `down` restores `head_user_id` before any earlier `down`
runs.

### 3.2 D6 member scoping — the security core (exact per-endpoint spec)

Every read is gated by **auth-context user id + membership role**, never a
client scope. The scoping rule per endpoint:

| Endpoint | Admin | Member | Change in this WP |
|---|---|---|---|
| `GET /groups/:id/ledger` | all rows; optional `?user_id=` filter | own rows; `?user_id`≠self → **403** | **behavior:** 403 instead of silent narrow |
| `GET /groups/:id/balance` | every member's balance row | **only own balance row** | **NEW scoping — closes the D6 hole** |
| `GET /groups/:id/loans` | all; optional `?user_id=` | own; `?user_id`≠self → **403** | **behavior:** 403 instead of silent narrow |
| `GET /groups/:id/allowances` (base amounts) | all rows | own rows | rename only (already scoped) |
| `POST /groups/:id/ledger` | any member, approved | self only, pending; settlement/adjustment admin-only | rename only |
| `POST /ledger/:id/approve`,`/reject` | ✅ | 403 | rename only |
| `POST /groups/:id/loans` | for any member | own request only | rename only |
| `POST /loans/:id/approve`,`/reject`,`/close` | ✅ | 403 | rename only |
| `PUT /groups/:id/allowances/:userId` | ✅ | 403 | rename only |
| `POST /groups/:id/chores`, `PATCH/DELETE /chores/:id` | ✅ | 403 | rename only |
| `GET /groups/:id/chores` | catalog | catalog | **unchanged** — chores are group reference data, not a member's private money |
| `GET /groups/:id/members`, `GET /groups/:id`, `GET /groups` | full | full / per-caller summary | **unchanged** — member list carries no amounts; `GET /groups` summary_balance is already per-caller |
| `POST /groups/:id/members` (add-by-email) | ✅ | 403 | rename only (V3-2.1; **no regression**) |
| `DELETE /groups/:id/members/:userId` | remove non-admin | leave (self) only | rename only |
| `POST /groups/:id/invite` | ✅ (D8 kept) | 403 | rename only |

**Error contract for all denials:** `403` with body
`{"error":"members can only access their own data"}` (cross-member reads);
existing "only group admin can …" 403s for admin-only writes. **Not 404** — the
charter mandates 403 for another member's data.

> **Statement endpoint is NOT in this WP** — `GET /groups/:id/statement` is
> V3-3.1 (Phase 3). It must adopt the identical member/admin scoping pattern;
> flagged for that spec.

#### 3.2.1 `GetBalance` — close the hole (`backend/internal/handlers/ledger.go`)

Today `GetBalance` discards the membership (`_, err = h.groupRepo.GetMember(…)`)
and returns **all** balances. Capture the member and filter:

```go

        continue // D6: a member sees only their own balance row
    }
    response = append(response, BalanceResponse{
        UserID:  b.UserID,
        Name:    b.Name,
        Balance: models.NewMoney(currency, b.Balance),
    })
}
c.JSON(http.StatusOK, response)
```

(`GetBalanceForGroup` already excludes the admin, so a member gets exactly their
own single row; an admin gets every member.)
