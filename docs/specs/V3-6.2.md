## 2. `app/eas.json` — the build config

Create **`app/eas.json`** (EAS reads it from the app root, next to `app.json`). Exact content:

```json
{
  "$schema": "https://raw.githubusercontent.com/expo/eas-cli/main/packages/eas-json/schema/eas.schema.json",
  "cli": {
    "version": ">= 12.0.0",
    "appVersionSource": "local"
  },
  "build": {
    "preview": {
      "distribution": "internal",
      "channel": "preview",
      "android": {
        "buildType": "apk"
      },
      "ios": {
        "simulator": false
      },
      "env": {
        "EXPO_PUBLIC_API_URL": "https://your-server.example.com/api/v1"
      }
    },
    "production": {
      "distribution": "store",
      "channel": "production",
      "autoIncrement": true,
      "android": {
        "buildType": "app-bundle"
      },
      "env": {
        "EXPO_PUBLIC_API_URL": "https://your-server.example.com/api/v1"
      }
    }
  }
}
```

**Why each field is what it is (bake this reasoning into the PR body, not the JSON — JSON has no
comments):**

- **`cli.appVersionSource: "local"`** — version comes from `app.json` (`expo.version` / Android
  `versionCode`), not EAS's remote version service. A self-hosting operator has no reason to depend on
  Expo-hosted version state; `local` keeps the build reproducible from the repo. (Newer EAS CLIs
  *require* `appVersionSource` to be set — omitting it is itself a warning.)
- **`cli.version: ">= 12.0.0"`** — a floor, not a pin; any modern EAS CLI satisfies it. Do not pin an
  exact version we haven't verified against SDK 54.
- **`preview` profile — the deliverable of this WP:**
  - `distribution: "internal"` → EAS produces a directly installable artefact + a shareable
    install page / QR (no App Store / Play Store, no TestFlight review). This is the "sideload an APK"
    path the acceptance row wants.
  - `android.buildType: "apk"` → a single `.apk` the operator sideloads onto a device, **not** an
    `.aab` (which is store-only and not directly installable). This is the crux for Android.
  - `ios.simulator: false` → the iOS preview build is a real device build (ad-hoc/internal). iOS
    internal distribution additionally needs Apple provisioning — flagged as an operator step (§7);
    for local iOS QA the checklist points at `npx expo run:ios` (simulator) instead.
  - **`env.EXPO_PUBLIC_API_URL`** → the **build-time** API base, baked into the JS bundle inside the
    binary (per §1). The committed value is a **placeholder** (`https://your-server.example.com/api/v1`)
    that the operator **must edit to their own server** before building, or override with an EAS
    environment variable. The README section (§4) states this in step 1, in bold. Committing a real
    URL here would be wrong — it varies per operator and would silently ship the wrong endpoint.
- **`production` profile — included because it is warranted** (the acceptance row says "note the
  production profile if warranted"): it is the store-track counterpart — `distribution: "store"`,
  `android.buildType: "app-bundle"` (Play Store requires AAB), `autoIncrement` for store version
  bumps. It documents intent and is a no-cost addition; the operator uses `preview` for sideloading
  and `production` only if/when they publish to a store. Same `EXPO_PUBLIC_API_URL` placeholder note
  applies.
- **`channel`** ties each profile to an EAS Update channel of the same name — harmless if the operator
  never uses OTA updates, useful if they later do. Optional; keep it (it costs nothing and documents
  the mapping). If it trips any doctor/schema check on this SDK, drop it — the `env` + `distribution`
  + `buildType` fields are the load-bearing ones.

**Do NOT** add a `development` profile (it would imply `expo-dev-client`, which is not a dependency —
adding it to satisfy a profile is scope creep and a doctor risk). Preview + production only.

**Validation obligation (the gate, §0.2):** confirm `app/eas.json` parses as JSON and its shape
matches the eas.json build-profile reference. A convenient offline check:
`node -e "JSON.parse(require('fs').readFileSync('eas.json','utf8'))"` from `app/`, plus a visual
diff against the fields above. Do **not** gate on `eas build`/`eas config`/`eas build:configure` —
those require the operator's Expo login (§7).

## 3. `docs/qa-device-checklist.md` — on-device golden path (Android + iOS)

Create **`docs/qa-device-checklist.md`**. It is a human sign-off checklist (there is no emulator in
CI — §5 of the plan), so every item must be **concrete and checkable** (a tester ticks a box), not
vague ("looks fine"). Structure it as GitHub-task-list checkboxes grouped by area, with a short
preamble and a sign-off footer. The v3 golden path (from master-plan §8 Phase-6 / §5 screen map) is
the spine: **register → create INR + EUR groups → add member by email (shadow) → chores/base/loan →
month statement → record payment → notifications bell.** Cover it on **both** Android and iOS.

Required sections and representative items (implementer writes the full, concrete list — these are the
mandatory coverage points, phrased as checkable assertions):

**A. Build & install**
- [ ] Android: the `preview` APK installs via sideload (transfer `.apk` to device → "install unknown
  apps" allowed → installs and launches) **or** the EAS internal-distribution install page/QR.
- [ ] iOS: installs via EAS internal distribution (ad-hoc device) **or** runs via `npx expo run:ios`
  on a simulator / `npx expo run:ios --device` on a provisioned device.
- [ ] App launches to the auth screen without a crash or a red-box error.

**B. Icons & splash**
- [ ] Android launcher shows the **adaptive icon** (foreground on the `#4F46E5` background); not the
  default Expo icon.
- [ ] iOS home-screen icon is the app icon (`assets/icon.png`), correct on both light/dark home.
- [ ] The splash screen shows `splash-icon.png` centered (`contain`) on the configured background
  during cold start, then hands off to the app with no flash of a wrong color.

**C. Safe areas & platform chrome** (per §5 platform-adaptive rules)
- [ ] Status bar / notch: no content is drawn under the notch or status bar; headers clear it.
- [ ] Home indicator: the bottom tab bar and scroll content clear the iOS home indicator / Android
  gesture bar (insets applied — `useSafeAreaInsets`, verified on a notched device).
- [ ] Rotation stays portrait-locked (`orientation: "portrait"`).
- [ ] Android hardware/gesture **back** navigates sensibly (no dead-ends, no accidental app exit
  mid-flow); keyboard-avoiding forms don't cover the focused input.
- [ ] Touch targets are ≥44pt (buttons, tab bar, list rows are comfortably tappable).

**D. Auth & dashboard**
- [ ] Register a new account, then log in; token persists across an app restart (secure store).
- [ ] Dashboard shows "Groups you manage" / "Groups you're in"; per-group headline is in the group's
  **own currency** and never summed across currencies (D7).

**E. Create groups (multi-currency)**
- [ ] Create an **INR** group and a **EUR** group via the currency picker; copy makes clear the
  currency is permanent.

**F. Statement flow**
- [ ] Open a group (admin) → the **Statement**: month switcher works; one row per member showing
  `base + chores − EMI = payable · cleared · remaining`; group total on top.
- [ ] Switching to a past month shows that month's archived statement.
- [ ] Amounts render in the group currency with correct symbol/format (₹ / €), no `NaN`, no raw minor
  units.

**G. Add member by email (shadow)**
- [ ] Add a member by **email** (an address with no account yet) → a shadow member appears in the
  group; the sheet closes and the row shows.

**H. Add entry / chores / loan**
- [ ] Add-entry picker offers chore / adjustment / clearing / new loan; add a chore-based entry and an
  adjustment; they appear in the member's passbook and move the statement numbers.
- [ ] Create a loan; the member detail shows the loan card with EMI progress / repayment schedule.

**I. Record payment**
- [ ] Tap **Record payment** on a member row → the amount is **pre-filled with the remaining**;
  recording it decreases "remaining" and the sheet closes (a real state change, not just no error).

**J. Notifications bell**
- [ ] The header **bell** shows an unread **badge** after an action that notifies; opening the
  notifications list shows the item; marking read clears the badge. (In-app bell — not OS push.)

**K. Member view (claim)**
- [ ] Register the shadowed member's email → they claim the account → they see **their own**
  statement/passbook (own rows only, read-only) and "You'll receive €X / ₹X this month."

**Footer:** a sign-off block — device model, OS version, app version/build, profile used
(`preview`), tester, date, and pass/fail per platform. State plainly that this checklist **is** the
native acceptance gate (there is no emulator in CI) and must be run on at least one real Android and
one iOS device (or documented simulator run) before the plan is marked complete in V3-6.3.

## 4. README "Native App (Android APK)" section

2. **The build-time API URL (bold, unmissable):** before building, set the server URL the APK will
   talk to — it is **baked into the binary at build time and cannot be changed after install**. Two

   - Edit `app/eas.json` → `build.preview.env.EXPO_PUBLIC_API_URL` to the operator's server

3. **Cloud build (Expo account) — the primary path:**
   ```bash
   cd app
   npm install
   npx expo login                 # operator's Expo credentials (operator step)
   npx eas build --platform android --profile preview
   ```

   ```bash
   cd app
   npm install
   ```

   device with USB debugging or a running emulator). Mention `npx expo run:ios` as the iOS-simulator

5. **QA pointer:** after installing, run **`docs/qa-device-checklist.md`** on the device to sign off

## 6. Risks & invariants — get these exactly right

1. **`EXPO_PUBLIC_API_URL` is build-time for native, and it is baked from `eas.json` profile `env`,
   not the operator's shell.** EAS cloud builds do not inherit shell `EXPO_PUBLIC_*`. So the value
   *must* be in `eas.json` (or an EAS env var) — the placeholder + the bold README step 2 are how the
   operator avoids shipping an APK pointed at `your-server.example.com`. The **local**
   `npx expo run:android` path is the exception: there Metro runs on the operator's machine and *does*
   read the shell/`.env` value (hence the `EXPO_PUBLIC_API_URL=… npx expo run:android` form).
2. **APK, not AAB, for sideloading.** `preview.android.buildType` must be `"apk"`. An `.aab` is not
   directly installable — using it would defeat "operator can produce an installable APK".
3. **`internal` distribution, not `store`,** for `preview` — otherwise EAS expects store credentials
   and there is no shareable install artefact.
4. **Do not add a `development` profile / `expo-dev-client`.** It's a dependency + doctor risk for no
   benefit here. Preview + production only.
5. **expo-doctor must stay clean.** Run `npx expo-doctor` from `app/` after adding `eas.json`. A
   stray/unknown field in `eas.json` or an `appVersionSource` omission can surface as a warning —
   fix by conforming to the schema, not by suppressing. If `channel` trips anything on SDK 54, drop
   it (§2).
6. **Never require an actual `eas build` to pass this WP.** The gate is expo-doctor + eas.json
   schema-shape + checklist committed + a verbatim-followable README. `eas build` (and iOS ad-hoc
   provisioning, and Apple/Expo accounts) is the **operator's step** — say so in the README and PR
   body. CI cannot and must not run it.
7. **Placeholder hygiene.** The committed `EXPO_PUBLIC_API_URL` is a clearly-fake placeholder
   (`https://your-server.example.com/api/v1`), never a real host, and never `localhost`
   (a localhost value would ship an APK that can only talk to the phone itself).
8. **Assets already exist** — do not regenerate or "improve" icons/splash; the QA checklist merely
   *verifies* the existing `assets/*` render on-device.
