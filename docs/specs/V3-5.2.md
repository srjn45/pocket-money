## 0. Summary

Give the app a **notifications bell** (icon + unread badge) in the header and a
**notifications list screen** that consumes the four V3-5.1 endpoints. Tapping a
notification marks it read and deep-links to its group (N-1 → the group the user
was added to); a **Mark all read** action clears the badge in one call. This is a
**FE-only WP**: no `backend/**`, no `openapi.yaml`, no migration. `npm run codegen`
is run only to pull the V3-5.1 schema additions into `app/src/api-types.gen.ts`
(generated file, never hand-edited — §9.1).

Nothing here touches auth, money, or nav invariants beyond adding one hidden route
and one header element. **No open question requires the brain** (§8).

## 1. What the backend gives us (V3-5.1 recap — the contract we consume)

All four endpoints are `BearerAuth`, scoped server-side to the caller's own
`user_id` (D6). No group in the path — notifications belong to users. See
`docs/specs/V3-5.1.md` §1 for the authoritative shapes; the FE-relevant surface:

| # | Call | Response |
|---|---|---|
| E1 | `GET /api/v1/notifications?limit=&cursor=` | `NotificationListResponse {items: Notification[], next_cursor: string\|null}`, newest first |
| E2 | `GET /api/v1/notifications/unread_count` | `UnreadCountResponse {count: int}` |
| E3 | `POST /api/v1/notifications/{id}/read` | `204` (idempotent, ownership-checked; a foreign/absent id → `404`) |
| E4 | `POST /api/v1/notifications/read_all` | `MarkAllReadResponse {updated: int}` |

`Notification = { id, type, payload, read_at: string|null, created_at }`.
`type ∈ {added_to_group, shadow_claimed, payment_recorded}` (N-1/N-2/N-3).
`payload` is free-form JSONB, **passed through verbatim**; the FE switches on
`type`. Confirmed payload shapes in this codebase (do **not** re-derive — read from
the running backend):

- **N-1 `added_to_group`** — `{ group_id, group_name, added_by_user_id }`
  (`backend/internal/handlers/groups.go:464`).
- **N-2 `shadow_claimed`** — `{ group_id, group_name, … }`
  (`backend/internal/handlers/auth.go:201`).
- **N-3 `payment_recorded`** — `{ group_id, group_name, amount: Money }`
  (`docs/specs/V3-5.1.md` §4.3; `amount` is `Money {currency, value}`, minor units, group currency — render via `AmountText`, never a bare int, D7).

**All three MVP types carry `group_id` + `group_name`.** That is the deep-link
key (§4.3) and the human-readable line source (§4.4). Cursor pagination is keyset
and opaque: treat `next_cursor` as a black-box string; `null` ⇒ last page.

### 1.1 Pagination scheme (as consumed)

- First page: omit `cursor`. Default page size is 20 (server clamps [1,100]); the
  FE **does not** send `limit` (accepts the server default) unless a smaller test
  page is wanted — keep it unset in app code.
- Next page: pass the previous response's `next_cursor` as `cursor`. Stop when
  `next_cursor` is `null`. This maps 1:1 onto `useInfiniteQuery`
  (`getNextPageParam: last => last.next_cursor ?? undefined`).

### 2.2 `app/src/api.ts` — add `notificationsApi` + type exports

The client is a **hand-written thin wrapper** over the generated *types* (it does
not consume generated operations — mirror the existing `statementApi`/`ledgerApi`
style). Add the type exports next to the others (`api.ts:28`):

```ts
export type Notification             = Schemas['Notification'];
export type NotificationListResponse = Schemas['NotificationListResponse'];
export type UnreadCountResponse      = Schemas['UnreadCountResponse'];
export type MarkAllReadResponse      = Schemas['MarkAllReadResponse'];
```

Add the API object after `statementApi` (`api.ts:223`):

```ts
// Notifications API (V3-5.1 endpoints; consumed by the V3-5.2 bell + list screen).
// User-scoped server-side (D6): every call returns/mutates only the caller's own
// notifications. `cursor` is opaque keyset paging (null ⇒ last page).
export const notificationsApi = {
  list: (cursor?: string | null) =>
    request<NotificationListResponse>(
      `/notifications${cursor ? `?cursor=${encodeURIComponent(cursor)}` : ''}`,
    ),

  unreadCount: () => request<UnreadCountResponse>('/notifications/unread_count'),

  // 204 No Content; request() already maps 204 → undefined. Idempotent server-side.
  markRead: (id: string) =>
    request<void>(`/notifications/${id}/read`, { method: 'POST' }),

  markAllRead: () =>
    request<MarkAllReadResponse>('/notifications/read_all', { method: 'POST' }),
};
```

`request()` already force-logs-out on `401` and maps `204`→`undefined`
(`api.ts:58,72`) — no special handling needed. A `404` from `markRead` (foreign/
absent id) surfaces as a thrown `Error` and is swallowed by the mutation's
`onError` (§3.3) — the row simply stays as-is; this cannot happen for the caller's
own rows.

## 3. Data layer — query keys + hooks

### 3.1 `app/src/query-keys.ts`

Add two keys (append to `qk`):

```ts
// Notifications (V3-5.2). The list is an infinite (paged) query; the count is the
// badge source. Mark-read / mark-all-read invalidate BOTH so the badge and the

notifications: () => ['notifications', 'list'] as const,

```

### 3.2 `app/src/hooks/useNotifications.ts` (new)

Four hooks. Follow the `useStatement`/`useGroups` conventions (react-query,
`enabled`, `qk`). No `groupId` — these are user-global.

```ts
import { useInfiniteQuery, useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { notificationsApi } from '../api';
import { qk } from '../query-keys';

// Paged list, newest first. Pages flatten in the screen via data.pages.flatMap(p => p.items).
export function useNotifications() {
  return useInfiniteQuery({
    queryKey: qk.notifications(),
    queryFn: ({ pageParam }) => notificationsApi.list(pageParam),
    initialPageParam: null as string | null,
    getNextPageParam: (last) => last.next_cursor ?? undefined,
  });
}

// Badge source. staleTime kept modest so re-entering the app / a screen refocus
// re-reads it; also invalidated explicitly by the mark mutations below.
export function useUnreadCount() {
  return useQuery({
    queryKey: qk.unreadCount(),
    queryFn: () => notificationsApi.unreadCount(),
    staleTime: 30_000,
  });
}

export function useMarkNotificationRead() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: string) => notificationsApi.markRead(id),
    onSuccess: () => {
      qc.invalidateQueries({ queryKey: qk.notifications() });
      qc.invalidateQueries({ queryKey: qk.unreadCount() });
    },
  });
}

export function useMarkAllNotificationsRead() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: () => notificationsApi.markAllRead(),
    onSuccess: () => {
      qc.invalidateQueries({ queryKey: qk.notifications() });
      qc.invalidateQueries({ queryKey: qk.unreadCount() });
    },
  });
}
```

Notes:
- **No polling requirement.** The badge refreshes on mount, on screen focus (query
  refetch), and after any mark mutation. Live push is out of scope (D4: in-app
  only). The e2e forces a fresh read with an explicit reload (§6), exactly as the
  existing suite does for the 30s staleTime (`reloadInto`, `pages.ts:185`).
- Keep the mutations **invalidate-only** (no optimistic cache surgery) — the list
  is small and the extra round-trip is imperceptible; simplicity over optimism.

### 3.3 `app/src/notification-format.ts` (new) — presentational mapping

One pure, unit-testable function maps a `Notification` → the display model, so the
screen stays declarative and every `type` has an explicit line (no "unknown type"
crash). Keep copy short (family-app tone, house style):

```ts
import type { Notification, Money } from './api';

export type NotificationView = {
  icon: string;          // Ionicons name
  title: string;
  body: string;
  groupId: string | null; // deep-link target (null ⇒ non-navigable)
};

export function formatNotification(n: Notification): NotificationView { … }
```

Mapping (drive copy off `payload.group_name`; `amount` via the money formatter):

| `type` | icon | title | body | groupId |
|---|---|---|---|---|
| `added_to_group` (N-1) | `people` | "Added to a group" | `You were added to ${group_name}.` | `payload.group_id` |
| `shadow_claimed` (N-2) | `person-add` | "Member registered" | `A member of ${group_name} just registered.` | `payload.group_id` |
| `payment_recorded` (N-3) | `cash` | "Payment recorded" | `${AmountText(amount)} was recorded as paid to you in ${group_name}.` | `payload.group_id` |
| _unknown_ (forward-compat) | `notifications` | "Notification" | "" | `null` |

- `payload` is typed loosely (`Record<string, unknown>` / narrowed per type) since
  the generated `Notification.payload` is free-form `additionalProperties`. Guard
  each field read; fall back to the _unknown_ row rather than throw.
- The N-3 amount is a `Money` object — format it with the shared formatter used by
  `AmountText` (extract or reuse the minor-units→string logic; **never** `parseFloat`
  or hardcode a symbol — §9.6, D7). A tiny `notification-format.test.ts` covering
  the three types + the unknown fallback + a EUR N-3 amount is expected (mirrors
  `loan-format.test.ts`).

## 4. UI

### 4.1 Where the bell lives (§5 platform-adaptive)

The app shell (V3-4.1) has **no single global header component**: the `(app)` group
is a `Tabs` navigator with `headerShown:false`, and each screen renders its own
in-body header (Dashboard/Profile) or its own `Stack` header (groups)
(`app/app/(app)/_layout.tsx:25`). The **shared component tree is the cross-platform
guarantee** (§5): an element placed in the in-body header renders identically on
web, Android, and iOS from one source, and the web e2e is the behavioral gate for
all three.

**Decision:** the bell is a reusable `HeaderBell` component placed in the
**Dashboard in-body header** (`app/app/(app)/index.tsx:133`, the `styles.header`
`View`) — the post-login landing surface, and exactly where the §8 e2e observes it.
`HeaderBell` is a shared RN component (no `Platform`-split, no native `Stack`
`headerRight` wiring), so it is one implementation across all three targets.

> Scope note (explicit, to keep the WP tight): the bell is **not** added to the
> group `Stack` header or the Profile header in this WP. The Dashboard is the app's
> home header and satisfies "bell in the app header" (§3.7) on all three platforms.
> Extending the bell to other headers is a follow-up, noted in `docs/notes/` if
> desired, not done here (§9.2 stay-in-WP).

### 4.2 `app/src/components/HeaderBell.tsx` (new)

- Renders a `Pressable` (touch target ≥44pt — §5) wrapping an Ionicons
  `notifications-outline` bell, testID **`header-bell`**.
- `useUnreadCount()` drives a badge overlay: when `count > 0`, render a small
  danger-tone (`theme.color.danger`) circle with the count as text, testID
  **`header-bell-badge`**. Cap the display at `99+` (`count > 99 ? '99+' : count`).
  When `count === 0` (or the query is loading/errored), **render no badge at all**
  (so the e2e asserts presence/absence via `toHaveCount`).
- `onPress` → `router.push('/(app)/notifications')`.
- Theme tokens only, no inline hex (§9.8). Export from `components/index.ts`.

### 4.3 `app/app/(app)/notifications.tsx` (new) — the list screen

Registered as a **hidden** `(app)` tab (not a visible tab button), mirroring how
the `groups` folder is hidden. In `app/app/(app)/_layout.tsx` add, alongside the
existing `groups` hidden screen (`_layout.tsx:35`):

```tsx
<Tabs.Screen name="notifications" options={{ href: null, headerShown: false }} />
```

`router.push('/(app)/notifications')` navigates to it; `href:null` keeps it out of
the bottom bar / top nav. It owns its header in-body (like Dashboard), so every
interactive control is a testID'd element in the shared tree (best for e2e +
cross-platform consistency).

Structure:

- `ScreenContainer` root, testID **`notifications-root`** (centered 700px column on
  web via `ScreenContainer`, full-bleed native — §5, free from the container).
- **In-body header row** containing:
  - Back control, testID **`notifications-back`** →
    `router.canGoBack() ? router.back() : router.replace('/(app)')` (robust on
    native where a hidden-tab leaf may have no pop target; web uses history).
  - Title "Notifications".
  - **Mark all read** action, testID **`notifications-mark-all-read`**, calls
    `useMarkAllNotificationsRead().mutate()`. Disable/hide it while
    `useUnreadCount().data?.count === 0` (nothing to clear); still keep it mounted
    with `count>0` so the e2e can find it. On success, show a toast (`useToast`,
    house kit — no `Alert.alert`, §9.8).
- **List** (`FlatList`) of `data.pages.flatMap(p => p.items)`:
  - Each row is a `Pressable`, testID **`notification-row-${id}`**, rendering the
    `formatNotification` icon/title/body. An **unread dot** (testID
    **`notification-unread-${id}`**) is rendered only when `read_at === null`.
  - Row `onPress` = the **mark-read-on-open** behavior (§4.4).
  - `onEndReached` → `fetchNextPage()` when `hasNextPage` (keyset paging via the
    infinite query). A footer spinner while `isFetchingNextPage`.
  - **Empty** state (`EmptyState`, testID **`notifications-empty`**): icon
    `notifications-outline`, "No notifications yet." **Loading** (`LoadingSpinner`)
    and **error** (`ErrorMessage` with retry) states — every list owes all three
    (§9.8).

### 4.4 Behaviors

**Mark-read-on-open (per-notification).** Tapping a `notification-row-${id}`:
1. Fire `useMarkNotificationRead().mutate(id)` (E3; idempotent — safe on an
   already-read row). This invalidates the list + unread count (§3.2), so the row's
   unread dot clears and the bell badge decrements/disappears.
2. **Deep-link:** if `formatNotification(n).groupId` is non-null, immediately
   `router.push('/(app)/groups/${groupId}')`. Per §8 acceptance, **N-1 deep-links
   to the referenced group**; the same rule applies to N-2/N-3 (all carry
   `group_id`). A notification with no `group_id` just marks read and stays on the
   list. Navigation and the mark mutation both fire on tap — the mutation is
   fire-and-forget (its invalidation lands whether or not we navigate away).

**Mark all read (bulk).** `notifications-mark-all-read` → E4 in one call; badge →
0, all rows' unread dots clear (via invalidation). This is distinct from
mark-read-on-open (per the §8 acceptance listing both).

**Money / currency (D7).** N-3 amounts render only through the shared money
formatter — no bare ints, no hardcoded symbol (§9.6). The formatter picks the
symbol from `amount.currency`.

### 6.2 New spec — `e2e/tests/notifications.spec.ts`

The §8 acceptance path: **add a registered user to a group → that user's bell shows
1 → open → marked read.** N-1 fires only for **registered** users (a shadow add
writes no notification), so the member must register *before* being added.

```
test('notifications bell: registered member added to group → bell shows 1 → open → deep-links + marked read'):
  1. Admin registers (context A) and creates a group; capture gid = groupIdFromUrl.
  2. Member registers in a fresh context B (uniqueEmail) → lands on dashboard-root.
     Assert B has NO badge yet: getByTestId('header-bell-badge').toHaveCount(0).
  3. Admin (A), inside the group, addMemberByEmail(memberEmail, 'Member') →
     the member is already registered, so N-1 is inserted for them.
  4. Member (B): reloadInto(page, 'dashboard-root')  // force fresh unread fetch
     (react-query 30s staleTime — same reason golden-path uses reloadInto).
     Assert badge visible AND count is 1:
       await expect(B.getByTestId('header-bell-badge')).toHaveText('1', {timeout:15_000}).
  5. openNotifications(B) → notifications-root visible; exactly one row:
       await expect(B.getByTestId(/^notification-row-/)).toHaveCount(1);
     capture its id; assert the unread dot present:
       await expect(B.getByTestId(`notification-unread-${id}`)).toBeVisible().
  6. Tap the row → deep-links to the group (state change = group screen visible):
       await B.getByTestId(`notification-row-${id}`).click();
       await expect(B.getByTestId('group-overview-root')).toBeVisible({timeout:15_000});
     (URL also contains `/groups/${gid}` — assert as a secondary check.)
  7. Marked read: go home and assert the badge is gone (count 0 ⇒ no badge node):
       await B.goto('/');
       await expect(B.getByTestId('dashboard-root')).toBeVisible({timeout:15_000});
       await expect(B.getByTestId('header-bell-badge')).toHaveCount(0, {timeout:15_000}).
  finally: close context B.
```

A **second, lighter test** exercises **mark-all-read** (optional but recommended,
cheap): seed ≥1 unread the same way, `openNotifications`, click
`notifications-mark-all-read`, assert the badge clears (`header-bell-badge`
`toHaveCount(0)`) and each row's unread dot is gone. Keep it self-provisioning and
`fullyParallel`-safe (unique emails, no seed dependency).

Assertions follow §9.12: success is a **state change** — a specific badge count, a
row count, the group screen mounting — never absence-of-failure. Group nav after
tap lands on `group-overview-root` (the deep-link target), which is the observable
proof of N-1's behavior.

### 6.3 Determinism notes (learned invariants)

- **Reload to observe the badge** (step 4): the member's dashboard mounted *before*
  the notification existed; react-query's 30s staleTime means no auto-refetch —
  `reloadInto` forces it, exactly as existing tests do (`pages.ts:185`).
- **AuthGate race** (§ project memory / golden-path §4.1): await `dashboard-root`
  after each register/claim before any further nav.
- **Fresh contexts** isolate the two users' storage/tokens (browser localStorage) —
  reuse `browser.newContext()` as golden-path does for the member.
